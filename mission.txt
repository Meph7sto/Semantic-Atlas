 预处理与解析 (Frontend -> Backend)

动作: 你的点击触发 /api/analysis/analyze_transcript/stream 接口请求。

处理: 后端接收文本，调用 

parse_transcript_to_spans

 将原始文本解析为“片段 (Spans)”。

这会处理 [start-end] speaker content 格式，如果没有时间戳则自动估算。

存储: 这些基础片段会被立即存入数据库 (upsert_spans)，作为后续分析的原子单位。

上下文构建 (Context Building)

关系构建: 系统会分析片段间的逻辑关联 (build_relations)。

打包 (Bundling): 根据上下文窗口限制和逻辑关系，将多个片段组合成一个 Bundle (处理包)。这就解释了为什么前端进度条会显示 "Bundle x/Total"。

AI 推理与抽取 (Inference Loop)

流式请求: 系统按顺序处理每个 Bundle。

模型调用: 对于每个 Bundle，调用 AI 模型 (

generate_toolcalls

)。

指令生成: 模型不是直接返回“需求文本”，而是返回一系列 Tool Calls (工具调用指令)。

例如：create_requirement(title="...", statement="...", level="L2")

例如：link_requirement_evidence(requirement_id="...", span_id="...")

执行与存储 (Execution & Storage)

指令解析: 

ToolCallExecutor

 接收 AI 返回的指令。

原子化写入: 执行器将这些指令转化为数据库操作：

创建需求: 在数据库中插入新的需求记录。

建立溯源: 将需求与原始的文本片段 (Span) 建立外键关联 (link_requirement_evidence)，实现“需求-原文”的可追溯性。

标记状态: 记录哪些片段已被处理 (mark_span_processed)。

结果反馈 (Feedback)

流式推送: 在上述执行过程中，后端通过 Server-Sent Events (SSE) 实时将进度（chunks, bundle_done）推送到前端。

最终渲染: 所有 Bundle 处理完成后，前端收到完整的结构化数据（包含需求列表、原文佐证、覆盖率），并在右侧面板渲染出来。

1) 要实现的后端 API（Flask）
========================
1.1 非流式接口（用于简单调试）
POST /api/analysis/ingest_transcript
Request JSON:
{
  "session_id": "可选；不传则后端生成",
  "transcript_text": "必填，会议转写全文",
  "options": {
     "estimate_timestamps_if_missing": true,
     "default_span_ms": 8000,
     "max_spans_returned": 200
  }
}

Response JSON:
{
  "success": true,
  "data": {
    "session_id": "...",
    "span_total": 123,
    "warnings": [ ... ],
    "spans_preview": [ 前 max_spans_returned 条 span ],
    "stats": { "has_timestamp_ratio": 0.7, "speaker_count": 3 }
  }
}

1.2 SSE 流式接口（前端正式用）
POST /api/analysis/ingest_transcript/stream
- Content-Type: application/json
- 响应为 text/event-stream
- 事件（event 字段统一放在 data JSON 里）：
  a) init：{event:"init", session_id, received_chars, received_lines}
  b) parsed：{event:"parsed", session_id, span_total, warnings, stats}
  c) db_upserted：{event:"db_upserted", session_id, upserted_count}
  d) final：{event:"final", data:{session_id, span_total, warnings, spans_preview, stats}}

注意：SSE 事件格式使用
data: <json>\n\n
并设置 headers: Cache-Control=no-cache, X-Accel-Buffering=no

========================
2) Transcript -> Spans 解析器规范（核心）
========================
2.1 输入允许的格式（至少支持两类）
A. 带时间戳 + 说话人（推荐）
[00:00:03-00:00:12] 张三: 我们要支持手机端上传音频
[1200-2400] 李四 需求要可追溯到原文

B. 无时间戳 + 说话人轮次（常见）
张三：我们要支持手机端上传音频
李四：需求要可追溯到原文

额外容错：
- 时间戳分隔符可能是 "-"、"~"、"—"
- 说话人后可能是 ":" / "：" / 空格
- 有的行可能只有文本没有 speaker：当 speaker 缺失时 speaker="unknown"
- 空行、无意义行（只含标点）应跳过
- 文本过长可以按句号/分号拆成多个 span（可选，但要稳定）

2.2 Span 输出字段（写入 DB）
每条 span 至少包含：
{
  "span_id": "<稳定唯一>",
  "session_id": "<session_id>",
  "start_ms": int | null,
  "end_ms": int | null,
  "speaker": string | null,
  "text": string,
  "asr_confidence": null,
  "meta_json": "<json string，可存 warnings/parse_source/line_no 等>"
}

2.3 稳定 span_id（幂等关键）
- span_id 必须对“同一个 session_id + 同一份 transcript_text”重复解析时稳定不变
- 推荐：sha256( session_id + "|" + start_ms + "|" + end_ms + "|" + speaker + "|" + normalized_text )
- normalized_text 至少做：trim、连续空白归一、全角冒号归一等（保证稳定）

2.4 时间戳缺失时的估算策略（要稳定）
- 若 estimate_timestamps_if_missing=true：
  - 使用 span_index * default_span_ms 作为 start_ms
  - end_ms = start_ms + default_span_ms
- 若 estimate_timestamps_if_missing=false：start_ms/end_ms 置 null
- 估算策略必须只依赖输入文本顺序，保证每次解析一致

2.5 解析 warnings
- 如：某行无法解析时间戳、speaker 缺失、发现重叠时间窗、出现 start_ms>end_ms 等
- warnings 既要返回给前端，也要存入 meta_json（便于审计/回放）

========================
3) 数据库（PostgreSQL）
========================
3.1 表结构
- 至少确保 spans 表存在（span_id 主键；session_id 索引）
- 可以复用已有 DDL，但要保证“启动即自动建表（只执行一次）”，不要让用户手工跑 SQL

3.2 Upsert 语义
- 以 span_id 为主键 upsert
- 同 span_id 再次写入时允许更新 text/speaker/start_ms/end_ms/meta_json（但不改变证据文本除非完全相同；建议：若 text 不同则记录冲突并拒绝更新，避免证据被覆盖）
- 返回 upserted_count（插入+更新数量）
