# Requirement Classification Agent Design

## Increment

- Name: `requirement-classification-agent`
- Date: `2026-03-29`

## Goal

在当前仓库真实已落地的 Agent 骨架之上，新增一个独立的 `requirement_classification_agent`，负责对单条需求执行以下分类判断：

- `L1 / L2 / L3 / L4`
- `功能 / 非功能`
- `领域标签`
- `优先级初判`

该 Agent 必须优先模仿当前仓库已实现的 3 个 Agent，而不是按理想化文档重新发明新基础设施。

## Why This Increment Exists

`.context/PROJECT.md` 已明确当前仓库最值得继承的能力是以下 3 个已落地 Agent 的统一实现骨架：

- `session_controller`
- `requirement_agent`
- `conflict_detection_agent`

同时，`docs/agent设计类型.md` 已将“需求分类 Agent”列为目标专项 Agent，并明确其职责为：

- `L1/L2/L3/L4`
- `功能/非功能`
- `领域标签`
- `优先级初判`

当前仓库虽然已有分类能力，但真实已落地的只是离线分类链路：

- `backend_business/api/routers/classification.py`
- `backend_inference/routers/classification.py`
- `frontend/src/views/alpha/Classification.vue`

该链路本质上是“文本/CSV -> 单标签分类结果”的工具型页面，不是 Agent，也没有 session、message、runtime graph、总控委托和父图内联写入能力，因此不能直接等同于本增量目标。

## Source-of-Truth Constraints

本设计严格服从以下仓库级约束。

### 1. Follow real code, not ideal docs

当设计文档与当前代码不一致时，以当前代码为准。新 Agent 必须仿照以下真实目录与运行方式：

- `backend_business/services/agent/agents/session_controller/`
- `backend_business/services/agent/agents/requirement_agent/`
- `backend_business/services/agent/agents/conflict_detection_agent/`

### 2. Keep the current three-layer split

- `frontend/` 负责调试页、SSE 消费、执行图可视化
- `backend_business/` 负责会话、编排、runtime graph、权限、路由
- `backend_inference/` 负责现有分类模型与通用 LLM 推理能力

### 3. Respect the write boundary

当前仓库唯一已明确稳定的需求写入路径仍然是 `requirement_agent -> RequirementActor`。因此本增量首版中的 `requirement_classification_agent` 只做只读分析，不直接写 `manage_requirements`，也不通过 Actor 修改需求状态。

### 4. Mimic existing agent shape exactly

新 Agent 首版必须具有与现有 Agent 同层级的要素：

- 独立 service
- 独立 prompt builder
- 独立 tool loop runner
- 独立 runtime graph recorder
- 独立 FastAPI router
- 独立前端 Alpha 调试页
- 独立 API 封装
- 对应单测与 contract 测试

### 5. Reuse the current inline delegation pattern

若接入 `session_controller`，必须复用当前已实现的“父图内联写入子 Agent 节点”的委托模式，不引入 MessageBus、Sidebar、invoke/waiting/return 的新运行时重构。

## Scope

### In scope

新增一个新的只读专项 Agent：

- agent type: `requirement_classification_agent`
- 单独会话
- 单独消息流
- 单独 runtime graph
- 支持被 `session_controller` 委托
- 输出结构化分类结论

### Out of scope

本增量不包含以下内容：

- 直接写 `manage_requirements.priority_suggested`
- 直接写 `tags`、`source_level`、`custom_fields`
- 新增 graph mode
- 新增执行拓扑模板
- 批量分类整个项目的 agent 工作流
- 重构旧的 `Classification.vue` 离线页面
- 推动全局 Agent 基础设施重构

## Recommended Architecture

选择“完整复刻版”方案：

1. 新增独立 `requirement_classification_agent`
2. 新增独立 router、前端页面、前端 API、测试
3. 在 `SessionControllerTools` 中增加 `invoke_requirement_classification_agent`
4. 继续沿用现有 inline tool-loop delegation

不选择以下方案：

- “只给旧 classification 路由套 agent 壳”
  - 原因：无法复刻现有 3 个 Agent 的 session/message/graph/runtime 形态
- “直接做 graph mode / topology mode”
  - 原因：超前于当前已稳定实现，违背 `PROJECT.md`

## Runtime Graph Shape

### Standalone classification agent

独立运行时容器配置建议：

- `human_input`
- `conductor`
- `requirement_classification_agent`

Recorder 行为仿照：

- `RequirementAgent` 的 `_RuntimeGraphRecorder`
- `ConflictDetectionGraphRecorder`

graph meta 首版建议包含：

- `intent: "pending"`
- `requirement_id`
- `resolved_requirement_id`
- `classification_result`

其中：

- `requirement_id` 表示用户显式传入的目标需求
- `resolved_requirement_id` 表示最终真实定位到的需求
- `classification_result` 用于最终前端摘要展示与图链恢复

### Session controller parent graph

当由 `session_controller` 委托时，父图 recorder 需新增一类容器：

- `requirement_classification_agent`

其节点写入方式必须复刻当前已有模式：

1. 在父图中创建 classification child start 节点，边类型为 `call`
2. 在同一张父图内运行 classification agent 的 tool loop round 节点
3. 创建 child end 节点
4. 写入 return edge
5. 恢复父节点 cursor

## Tool Boundary

工具边界应保持清晰，不使用“全能工具”。

建议工具列表：

### 1. `list_requirements`

职责：

- 在当前项目内分页列出需求摘要
- 用于探索性定位

返回形状对齐现有工具风格：

- `total`
- `start_index`
- `count`
- `has_more`
- `items`

### 2. `search_requirements`

职责：

- 在当前项目内按关键词搜索需求
- 用于从自然语言定位目标需求

### 3. `get_requirement_detail`

职责：

- 返回单条需求的完整内容

至少包含：

- `requirement_id`
- `title`
- `status`
- `priority`
- `parent_id`
- `requirement_type`
- `source_level`
- `description`
- `acceptance_criteria`
- `notes`
- `tags`

### 4. `classify_requirement`

职责：

- 针对一条已明确定位的需求输出四类分类结论

输入：

- `requirement_id`

输出：

- `requirement_id`
- `title`
- `level`
- `requirement_nature`
- `domain_tags`
- `priority_suggestion`
- `reasoning`
- `evidence`
- `raw_classifier_label`

## Classification Decision Strategy

`classify_requirement` 不是简单转发旧的 `/classification/predict-texts`，而是组合现有仓库能力后输出统一结论。

### Step 1. Load real requirement data

先通过 `RequirementsManageService` 读取真实需求对象。

### Step 2. Prefer structural fields for level

层级判定优先使用仓库已有结构字段：

- 如果 `source_level` 明确存在，则直接采用
- 否则如果 `requirement_type == "low_level"`，则判为 `L4`
- 否则交给后续补判

原因：

- 这遵循“先相信当前真实代码里的结构化数据”的原则
- 避免重新猜测已经存在的信息

### Step 3. Reuse existing classification model for base nature judgment

复用现有分类模型底判标签：

- `功能性需求` -> `functional`
- `性能需求` / `安全需求` / `可靠性需求` / `可用性需求` / `兼容性需求` / `可维护性需求` / `其他`
  -> `non_functional`

该模型原始标签保存在：

- `raw_classifier_label`

### Step 4. Use LLM to complete dimensions the classifier cannot cover

现有分类模型不能稳定覆盖：

- `L1/L2/L3/L4`
- `domain_tags`
- `priority_suggestion`

因此在工具内部再调用 `ai_proxy.chat_completion`，基于以下输入做结构化补判：

- 需求全文
- 已知结构字段
- 分类模型底判标签

模型输出必须是受限 JSON，字段固定为：

- `level`
- `requirement_nature`
- `domain_tags`
- `priority_suggestion`
- `reasoning`
- `evidence`

### Step 5. Validate and normalize output

工具层必须对 LLM 输出做严格校验与归一化：

- `level in {"L1", "L2", "L3", "L4"}`
- `requirement_nature in {"functional", "non_functional"}`
- `priority_suggestion in {"P0", "P1", "P2", "P3"}`
- `domain_tags` 必须为字符串数组
- `domain_tags` 数量首版限制为 `1..3`

若 LLM 返回脏结构，不直接透传到前端。

## Result Contract

首版统一结果结构如下：

```json
{
  "requirement_id": "REQ-123",
  "title": "系统应支持批量导入需求数据",
  "level": "L2",
  "requirement_nature": "functional",
  "domain_tags": ["需求管理", "导入导出"],
  "priority_suggestion": "P2",
  "reasoning": "该需求描述的是系统能力，属于功能需求，语义粒度更接近功能层。",
  "evidence": [
    "title: 系统应支持批量导入需求数据",
    "description: 支持 CSV 文件导入"
  ],
  "raw_classifier_label": "功能性需求"
}
```

## Prompt Design

PromptBuilder 必须延续现有 agent 风格：

- 系统提示词只定义职责边界与工具使用规则
- 用户消息只传当前轮任务上下文
- 不在 prompt 中扩展新的运行时概念

核心约束：

- 你是需求分类 Agent
- 你只能在当前项目内分类需求
- 你必须优先依赖工具结果
- 若目标需求不明确，先 list/search/get，再决定
- 当工具已经足够回答时，输出简洁中文，不输出 JSON
- 不做写操作

## Error Handling

错误处理沿用现有 agent 风格。

### Tool-level errors

- 需求不存在 / 已删除 -> `ValueError`
- 需求不属于当前项目 -> `ValueError`
- `keyword` 为空 -> `ValueError`
- `requirement_id` 为空 -> `ValueError`

### Classification failure strategy

首版允许分类模型不可用时退化为 LLM-only 补判，但必须显式标识：

- `raw_classifier_label = null`

如果 LLM 输出也无法校验，则整个工具失败，不返回伪造结论。

### Clarification strategy

如果用户未明确指定需求，且 `list/search/get` 后仍无法定位唯一需求，则停止分类并以最小必要问题澄清。

## Implementation Sequence

实现顺序建议如下：

1. 新增 `requirement_classification_tools.py`
2. 新增 classification agent 的 `prompt_builder / tool_loop_runner / runtime_graph_recorder / service`
3. 新增 router 并注册到 `backend_business/main.py`
4. 为 `session_controller` 增加 invoke 工具与 container
5. 新增前端 API 与 Alpha 页面
6. 补 tests

## Acceptance Criteria

完成后应满足以下标准：

1. 用户可以像现有 agent 一样创建并使用 classification agent 会话
2. classification agent 能在当前项目中定位目标需求并返回四维分类结果
3. 运行过程能写入 runtime graph，并在前端可视化
4. `session_controller` 能以内联方式委托 classification agent
5. 不引入新的写路径，不破坏 `requirement_agent` 的唯一写职责
6. 前后端和测试风格与现有 3 个 agent 保持同构

## Non-Goals For This Increment

以下内容即使未来可能需要，也不属于本增量：

- 自动把分类结果持久化回需求表
- 批量项目扫描与全库分类
- 分类结果审批流程
- GraphExecutor 版本 classification agent
- 统一多 Agent 共享分类缓存
- 前端正式 Beta 页面集成

## Final Decision

本增量的最终落点不是“包装旧分类接口”，而是：

新增一个和 `requirement_agent`、`conflict_detection_agent` 同等级、同风格、同运行时形态的第四个专项 Agent，并仅在其内部复用当前仓库已有的分类模型和通用 LLM 能力。
