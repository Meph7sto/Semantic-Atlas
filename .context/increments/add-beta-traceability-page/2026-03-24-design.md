# Beta Traceability Workbench Design

**Increment:** `add-beta-traceability-page`

**Goal:** Add a Beta traceability workbench for project and branch level requirement tracking without introducing destructive refactors or new business entities that do not already exist in the repository.

## Design Constraints

- Minimize invasive changes to existing repository behavior.
- Prefer adding new API aggregation methods and a new Beta view over restructuring existing manage, requirements, or product pages.
- Reuse existing business-domain models exactly as they exist today.
- Do not introduce external Git integration. The repository already uses Git-like concepts inside the requirement-management domain.
- Do not create new standalone task, defect, or repository-commit entities in this increment.

## Domain Interpretation

The existing management domain borrows Git mental models but does not integrate with a real Git provider:

- `milestone` is a snapshot of the managed requirement tree.
- `branch` points to a snapshot head for a project.
- `commit` is represented by milestone evolution edges and branch snapshot progression.
- `change set` records branch-scoped requirement changes.
- `merge` represents managed branch convergence between snapshots.
- `audit log` is business evidence, not source-control history.

This increment must preserve that meaning in API contracts, UI labels, and documentation.

## User-Facing Outcome

Add a new Beta page that serves as a project and branch scoped traceability workbench with four tabs:

1. `追溯矩阵`
2. `覆盖检查`
3. `影响分析`
4. `风险透视`

The page is entered from the Beta navigation and uses a shared `project + branch` context across all tabs.

## Information Architecture

### Page Shell

- Keep the current Beta shell pattern: `Sidebar`, `page-header`, `canvas`, `card`, `grid`.
- Provide a project selector and branch selector in the header.
- Keep a refresh action and an explicit impact-analysis trigger.
- Avoid mixing this experience into `RequirementsView.vue` or `ProductManageView.vue`; create a dedicated page instead.

### Traceability Matrix Tab

- Show branch-head requirement hierarchy as the primary structure.
- Display requirement status, test coverage, related change-set count, and recent audit evidence in a dense tree/table.
- Allow filtering by status, risk-only, uncovered-only, and keyword.
- Show a detail panel for the selected requirement with:
  - requirement details
  - bound test cases
  - related change sets
  - related audit logs
  - branch and snapshot context

### Coverage Tab

- Show project-level coverage summary cards.
- Show orphan requirements:
  - requirement status is `in_progress`
  - no linked test case exists
- Show unlinked changes:
  - change set does not reference a requirement
  - or references a missing requirement in the current project context

### Impact Analysis Tab

- Compute branch impact relative to a comparison target:
  - branch base milestone
  - current project baseline
  - or an explicit milestone
- Show:
  - milestone diff summary
  - changed requirements
  - affected descendant requirements
  - affected test cases
  - related change sets
  - related audit evidence
  - risk flags

### Risk Insight Tab

- Present management-oriented summaries:
  - requirement status distribution
  - uncovered in-progress requirements
  - frequently changed requirements
  - recently active audit targets
  - highest-risk chains based on impact and coverage

## Backend Design

Add traceability-specific aggregation behavior under the existing manage domain rather than inventing a separate service boundary.

### New Router Endpoints

Add new endpoints under `backend_business/api/routers/manage.py`:

- `GET /manage/projects/{project_id}/traceability/overview`
- `GET /manage/projects/{project_id}/traceability/matrix`
- `GET /manage/projects/{project_id}/traceability/coverage`
- `POST /manage/projects/{project_id}/traceability/impact`
- `GET /manage/projects/{project_id}/traceability/risk`

These endpoints should accept branch context, reuse existing permission checks, and return page-ready aggregated payloads.

### Service Additions

Add new aggregation methods inside `RequirementsManageService`:

- `get_traceability_overview`
- `get_traceability_matrix`
- `get_traceability_coverage`
- `create_traceability_impact_report`
- `get_traceability_risk`

Implementation should reuse existing methods where possible:

- `list_requirements`
- `list_test_cases`
- `list_branches`
- `list_change_sets`
- `list_audit_logs`
- `get_milestone`
- `compare_milestones`

Prefer small helper methods inside the existing service over broad refactors.

### Data Sources

Only use existing tables and models:

- `manage_requirements`
- `manage_test_cases`
- `manage_requirement_test_links`
- `manage_milestones`
- `manage_milestone_nodes`
- `manage_milestone_relations`
- `manage_milestone_edges`
- `manage_branch_refs`
- `manage_branches`
- `manage_change_sets`
- `manage_impact_reports`
- `manage_audit_logs`

## Frontend Design

### New View

Add a dedicated Beta page, for example:

- `frontend/src/views/beta/TraceabilityView.vue`

This page should:

- use the Beta shell and navigation composables
- load project and branch context once
- keep a single active-tab state
- fetch each tab from dedicated aggregation endpoints

### Suggested Supporting Files

- `frontend/src/api/traceability.js` or extend `frontend/src/api/project.js`
- `frontend/src/composables/useTraceabilityWorkbench.js`
- Beta components for:
  - context header
  - matrix panel
  - coverage panel
  - impact panel
  - risk panel

Keep component boundaries narrow and aligned to current repository patterns. Avoid migrating unrelated existing views to shared abstractions unless strictly required.

## Error Handling

- Reject access when project permission fails, using current manage router behavior.
- Return clear `404` style errors for missing project, branch, or milestone context.
- Return empty-state payloads for tabs when the project has no branches, no baseline, no tests, or no change history.
- Impact analysis should degrade gracefully when there is no comparison target; do not crash the page.

## Testing Strategy

### Backend

- Add focused API tests for each new endpoint.
- Add service tests for:
  - matrix aggregation
  - orphan coverage detection
  - unlinked change detection
  - impact calculation against milestone diffs
  - risk summary output

### Frontend

- Add focused tests for:
  - tab switching
  - project and branch context loading
  - matrix rendering with empty and populated data
  - coverage issue display
  - impact request and result rendering

## Implementation Strategy

To minimize breakage:

1. Add backend aggregation methods and router endpoints first.
2. Leave current endpoints unchanged.
3. Add the new Beta route and page as a separate entry.
4. Reuse existing API clients and composable patterns where possible.
5. Avoid schema churn unless existing tables cannot express the required result.

## Non-Goals

- External Git provider integration
- New task or defect entity models
- Refactoring current Beta manage pages into a new shared framework
- Replacing the existing requirement-management model vocabulary
