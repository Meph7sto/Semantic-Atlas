## 二、逐项详细对比

### 2.1 节点类型（NodeType）

**方案设计：**
- 执行图共 5 种节点类型：`start`、`llm`、`handoff`、`invoke`、`end`
- 拓扑节点只用其中 3 种：`llm`、`invoke`、`handoff`（start/end 由 container 边界隐含）

**代码实现（`agent_container.py` NodeType）：**
```python
class NodeType(str, Enum):
    START = "start"
    LLM = "llm"
    HANDOFF = "handoff"
    INVOKE = "invoke"
    END = "end"
```

> ✅ **已统一**：`NODE` 和 `DECISION` 已移除，数据库迁移自动将旧数据转为 `llm`。

### 2.4 complete_phase 机制

**方案设计：**
- `complete_phase` 是运行时为每个 `llm` 类型 subgraph 自动注入的专用工具
- 模型调用 `complete_phase` 并传入结构化结论 → 运行时 schema 校验 → 标记 subgraph 完成 → 激活出边
- 这是 **阶段完成的唯一信号**
- 与业务工具的核心区别：业务工具结果回填后模型继续推理；`complete_phase` 成功则终结当前 subgraph

**代码实现：**
- ✅ `ToolLoopRunner` 通过 `enable_complete_phase=True` 参数启用
- ✅ 运行时自动注入 `complete_phase` 工具定义（含 `conclusion` 和 `route_key` 参数）
- ✅ 模型调用 `complete_phase` 后立即中断 tool loop，返回 `ToolLoopResult(phase_completed=True)`
- ✅ 自动将 `conclusion` 追加到 Scratchpad 的 `stage_output` 条目
- ✅ `route_key` 字段可用于条件出边匹配
- ✅ 向后兼容：默认不启用，现有 Agent 不受影响

> ✅ **已实现**：`complete_phase` 工具已作为 `ToolLoopRunner` 的内置工具实现，与 `scratchpad_write` 采用相同的注入模式。
- ✅ `ToolLoopRunner` 通过 `enable_complete_phase=True` 参数启用

### 2.5 执行状态机

**方案设计（5 种状态）：**

| 状态      | 含义                 | 进入条件                         |
| --------- | -------------------- | -------------------------------- |
| Running   | 正在推进             | 初始 / 从 Waiting/Suspended 恢复 |
| Waiting   | 等待系统内部异步结果 | invoke 节点已发出调用            |
| Suspended | 等待用户外部输入     | handoff 触发 / 重试耗尽          |
| Succeeded | 正常结束             | end 节点完成                     |
| Failed    | 不可恢复错误         | 异常                             |

**代码实现（`topology_execution_service.py` + `graph_recorder.py`）：**
- `running`、`suspended`、`succeeded`、`failed` — 4 种状态

**差异分析：**
| 项目           | 说明                                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Waiting` 状态 | ❌ **未实现**。方案中 `Waiting` 与 `Suspended` 是两种本质不同的等待：`Waiting` 等系统内部结果（invoke 跨容器调用），`Suspended` 等用户输入。代码中没有区分这两种等待状态 |

### 2.6 Subgraph（子图）

**方案设计：**
- Subgraph 是 container 下的阶段对象，映射拓扑图中的一个节点
- 核心映射：拓扑图一个节点 = 执行图一个 subgraph
- Subgraph 内允许多个执行节点灵活伸缩
- Subgraph 完成由 `complete_phase` 触发
- 不是所有 node 都必须归属 subgraph

**代码实现：**
- ✅ 数据库表 `execution_subgraphs` 已存在，支持 CRUD
- ✅ `TopologyExecutionService._clone_template_to_runtime()` 会克隆 subgraph
- ✅ `ExecutionContext` 有 `begin_subgraph()` / `end_subgraph()` 生命周期方法
- 🟡 `RuntimeGraphRecorder` 中没有使用 subgraph 概念来组织阶段

**差异分析：**
| 项目                                | 说明                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------ |
| Subgraph 与拓扑节点映射             | 🟡 数据结构存在，但运行时没有实际的"一个拓扑节点 → 一个 subgraph"的映射执行逻辑 |
| Subgraph 完成判断                   | ✅ `complete_phase` 已实现，可通过 `enable_complete_phase` 启用                 |
| Subgraph 完成判断                   | ✅ `complete_phase` 已实现，可通过 `enable_complete_phase` 启用                 |
| Subgraph 在 RuntimeGraphRecorder 中 | ❌ recorder 按 "turn + round" 组织节点，不按 subgraph                           |
| task_description 字段               | ✅ subgraph 表有 `task_description` 字段，对应方案中的 `task_prompt`            |

### 2.8 上下文管理

**方案设计（两级策略）：**

| 级别   | 机制                        | 范围                                             |
| ------ | --------------------------- | ------------------------------------------------ |
| 第一级 | subgraph 内增量累积         | 同一 subgraph 内所有节点共享连续增长的上下文窗口 |
| 第二级 | 跨 subgraph Scratchpad 蒸馏 | 下游 subgraph 只能通过 Scratchpad 看到上游信息   |

Scratchpad 三类写入：
1. 模型自主备注（`note`）
2. 工具结果摘录（`tool_excerpt`，只读）
3. 阶段结构化产出物（`stage_output`，`complete_phase` 触发时自动追加）

**代码实现：**
- ✅ `Scratchpad` 类（`runtime/scratchpad.py`）完整实现了三类条目
- ✅ `ExecutionContext`（`runtime/context.py`）实现了 `begin_subgraph()` / `end_subgraph()` 两级策略
- ✅ `ToolLoopRunner` 注入了 `scratchpad_write` 工具
- ✅ `Scratchpad.append_stage_output()` 在 subgraph 结束时自动追加

**差异分析：**
| 项目                | 说明                                                           |
| ------------------- | -------------------------------------------------------------- |
| 跨 container 不可见 | ✅ Scratchpad 实例在 container 级别创建，天然隔离               |
| 第三类自动追加      | ✅ `complete_phase` 调用时自动追加 `stage_output` 到 Scratchpad |
| 第三类自动追加      | ✅ `complete_phase` 调用时自动追加 `stage_output` 到 Scratchpad |
| 下游 subgraph 读取  | ✅ `begin_subgraph()` 时注入 Scratchpad 快照                    |

> 上下文管理是**与方案最接近**的部分之一。

### 2.12 TopologyExecutionService（拓扑模板克隆与实例化）

**方案设计：**
- 拓扑图是可复用的**静态模板/蓝图**，描述某类任务"应当怎么跑"的结构约定
- 拓扑图本身不执行任何推理，LLM 推理由各 Agent 通过 ToolLoopRunner 独立完成
- 运行时实例化：拓扑图 → 执行图骨架（每个拓扑节点 → Pending subgraph）
- 一个拓扑节点 = 执行图中的一个 subgraph（结构映射关系）

**代码实现（`topology_execution_service.py`）：**
- ✅ 支持从模板克隆运行时图（`_clone_template_to_runtime`）
- ✅ 支持 container、subgraph、node、edge 的完整克隆
- ✅ 基本的节点遍历循环（`_run_runtime_graph`），用于验证图结构的连通性
- 🟡 `_execute_node()` 仅处理静态输出和透传，符合拓扑图作为静态模板的定位
- 🟡 条件出边评估使用 Python 表达式（`condition_expr`），方案中描述的是 complete_phase 路由匹配

**差异分析：**
> `TopologyExecutionService` 的核心职责是**模板克隆与实例化**，将拓扑图蓝图转化为运行时执行图骨架。这与方案中拓扑图作为静态模板的定位一致。实际的 LLM 推理、tool call 循环等执行逻辑由各 Agent 的 ToolLoopRunner 负责，不属于拓扑图的职责范围。

### 5.1 总体评估

拓扑图作为**静态模板/蓝图**，其数据结构层（容器、子图、节点、边的 CRUD 和结构建模）已基本与方案对齐。`TopologyExecutionService` 承担模板克隆与实例化职责，将拓扑图转化为运行时执行图骨架，符合方案中拓扑图的定位。LLM 推理由各 Agent 的 ToolLoopRunner 独立完成，不属于拓扑图的职责。
