2026-07-20 Agent 架构审查待处理项

以下问题来自对当前 graph/runtime、工具调度、Scratchpad 和 Actor 协调链路的静态审查。它们不要求推翻 graph-first 架构；优先目标是让运行时行为、并发语义和记忆预算与现有设计口径一致。

P0：LocalAgentRuntime 的实时流、取消和超时语义仍需收紧。
- `LocalAgentRuntime.stream()` 会先等待 runner 完成，再回放内存中的 events；跨 container 委托不能向上游实时转发阶段事件。
- `cancel()` / timeout 会先标记 run 终态并释放 quota，但 Python worker thread 与正在进行的外部调用只能协作式停止，可能继续运行或产生副作用。
- 建议引入 RunSupervisor：使用事件队列实时转发；将 cancelling 与 terminal 状态区分；只有 worker 确认退出后才释放配额。对于不可协作的调用，需要明确硬超时隔离策略。
- 验收：阻塞工具在完成前可被实时观察；取消后不会继续执行下一轮工具调用；timeout 后不会让仍在运行的任务绕过并发额度。

P0：ToolLoopRunner 缺少副作用工具的调度策略。
- 当前同一轮 tool calls 会逐个创建线程并行执行；能力策略只限制工具名称，不表达读写属性、资源键、幂等性或并发组。
- `update_requirement_content` 会创建审批请求，属于可观察副作用；多个针对同一 requirement 的调用可能并发产生重复审批或顺序漂移。
- 建议为工具声明 `read_only`、`idempotent`、`resource_key`、`concurrency_group` 等元数据：只读且资源独立的调用可并行，写操作按资源键串行，并设置每轮并发上限。
- 验收：同一 requirement 的写型工具严格有序；不同 requirement 的安全读操作仍可并发；工具结果保持稳定顺序。

P1：Scratchpad 缺少跨轮预算和选择性蒸馏。
- SessionController 创建新图时会复制上一图的完整 `snapshot_all()`；`Scratchpad.format_for_prompt()` 会拼接全部可见条目，并在子图开始时注入提示词。
- 长会话会导致上下文、延迟和模型成本持续增长，也会增加无关历史干扰当前阶段的概率。
- 建议增加 memory compiler / retrieval policy：按 container、任务、时效和重要度选择条目；设置 token 与条目上限；超预算时生成压缩摘要并保留原始 trace 供审计。
- 验收：长会话提示词大小有可观测上限；每个子图只收到与当前任务相关的记忆；原始历史仍可从 graph/state 查询。

P1：AgentRegistry 尚未成为唯一的 Agent 扩展边界。
- `AgentDefinition` 已声明 tool executor、context builder、result postprocessor 等扩展位，但当前 runtime 未统一消费这些字段。
- requirement、classification、conflict 的定义同时存在于 agent 包和 `runtime/agent_registry.py`；SessionController 仍维护手工 service 映射、委托工具名和图模板节点。
- `AgentExecutionService` 仍只有重构计划，没有实际实现；业务 service 继续同时承担 session、SSE、graph、持久化和业务适配职责。
- 建议保留单一 AgentCatalog：每个 Agent 自带唯一 definition、工具工厂、prompt/context/result adapter 和委托 metadata；由薄 application service 统一处理 session、recorder、SSE 与 assistant message 持久化。
- 验收：新增一个 Agent 不需要修改多个硬编码 map 或 switch；definition 改动只存在一个来源；公共执行路径通过同一 application service。

P1（仅多实例部署）：分布式 Actor 协调未形成完整闭环。
- Actor 已被远端实例持有时，当前实例会拒绝请求；`forward_request()` 尚未实现，因此无法路由到持有者。
- heartbeat 目前只刷新 instance key，没有续期实际 lock key；长时间运行后锁可能过期。
- 单进程部署不受此项影响。若要横向扩容，应在发布前完成带 fencing token 的原子续租、节点间命令路由和多实例集成测试；否则应把 Actor 部署约束明确为单实例。
- 验收：多实例下同一 requirement 始终只有一个活跃 Actor；请求可路由到持有者；锁续期、实例故障和恢复路径均可测试。
