# Agent 架构设计——Agent 方案

---

## 一、整体架构

### 1.1 分层结构

系统 Agent 层分为两层，职责严格隔离：

```
┌─────────────────────────────────────────────────────┐
│                     会话层                           │
│              会话总控 Agent                          │
│        （唯一入口 / 意图识别 / 流程管控）             │
└──────────────────────┬──────────────────────────────┘
                       │ 委托指令
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
┌───────────────┐ ┌──────────┐ ┌───────────────┐
│  需求管理      │ │  质检     │ │  冲突检测      │
│  Agent        │ │  Agent   │ │  Agent        │
│ （执行写操作） │ │（只读评判）│ │ （跨需求分析） │
└───────┬───────┘ └────┬─────┘ └───────┬───────┘
        │              │               │
        └──────────────┼───────────────┘
                       ▼
        ┌──────────────────────────────┐
        │         领域层               │
        │     RequirementActor         │
        │  （业务状态唯一权威持有者）    │
        └──────────────────────────────┘
```

**会话层**只有一个 Agent——会话总控。它是系统对用户的唯一界面，负责意图识别与流程编排，对需求工程领域语义不透明。

**执行层**有三个专项 Agent，各自只做一件事，不横向感知彼此，只响应来自会话总控的委托指令。

**领域层**的 `RequirementActor` 是所有需求数据的唯一权威持有者，任何 Agent 不得绕过 Actor 直接操作底层存储。

### 1.2 通信架构

Agent 之间的通信遵循以下规则：

**纵向通信（会话总控 ↔ 执行层 Agent）**

会话总控的上下文中预先注入了各专项 Agent 的调用工具（`invoke_requirements_agent`、`invoke_qa_agent`、`invoke_conflict_agent`）。会话总控通过 tool call 发起委托，Sidebar 作为 tool call 的接收端，负责将任务投递给可用执行器并将结果路由回来。会话总控不感知具体执行器实例，只关心 tool call 的结果。

**执行层 Agent 之间：不直接通信**

需求管理 Agent、质检 Agent、冲突检测 Agent 三者之间无任何直接调用关系。执行层 Agent 之间的协作逻辑（如“修改完成后触发质检”）完全由会话总控编排，执行层 Agent 只处理单一职责后向上返回结论。

**Agent → Actor 的读写边界**

只有需求管理 Agent 向 `RequirementActor` 发送写 Command。质检 Agent 和冲突检测 Agent 仅以强一致直读（Actor Ask）方式读取需求状态，不产生任何写操作。

```
会话总控
  ├─→ 需求管理 Agent ─→ RequirementActor（读 + 写）
  ├─→ 质检 Agent ──────→ RequirementActor（只读）
  └─→ 冲突检测 Agent ──→ RequirementActor（只读）
```

### 1.3 数据流转模型

一次典型用户指令的完整数据流：

```
用户自然语言输入
       ↓
会话总控（意图识别 → 生成结构化委托指令）
       ↓
执行层 Agent（接收指令 → 执行 → 返回结构化结论）
       ↓              ↑
  RequirementActor（Command / Actor Ask）
       ↓
  EventStore（追加不可变事件）
       ↓
  ReadModel（异步投影更新）
       ↓
会话总控（聚合结论 → 转为自然语言）
       ↓
用户回复
```

**关键设计：强一致读**

由于 `ReadModel` 通过异步订阅事件流更新，存在毫秒级延迟窗口。Agent 在推理过程中需要读取需求数据时，必须通过 Actor Ask 直接向 Actor 请求内存中最新状态，而非查询 `ReadModel`，确保 Agent 决策基于最新数据。

### 1.4 执行图视角下的运行单元

结合执行拓扑图模板与运行时执行图这两类抽象，本方案中的 Agent 协作关系可以进一步映射为统一的图结构。需要先明确两个概念：

| 概念           | 含义                                                           |
| -------------- | -------------------------------------------------------------- |
| 执行拓扑图模板 | 对某类任务的静态建模，描述容器、节点、边及其约束               |
| 运行时执行图   | 某条用户指令真实发生的执行轨迹，包含动态状态、重试、挂起、恢复 |

在本方案中，执行拓扑图模板负责定义静态约束，运行时执行图负责承载动态轨迹；两者共同构成 Agent 编排的统一抽象。核心映射关系如下：

| 图元素      | 在 Agent 方案中的语义                                      | 当前已支持的关键字段                                                            |
| ----------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `graph`     | 一类流程模板，如”修改需求并自动质检”                       | `name`、`description`、`status`、`layout_json`                                  |
| `container` | 一个 agent 的职责边界，对应一个具体角色                   | `container_key`、`label`、`role_type`、`config_json`                            |
| `subgraph`  | container 的子元素，对应拓扑图中的**一个可见节点**；内部包含若干执行节点，表达一个语义单元的完整实现 | `subgraph_key`、`label`、`nodes`、`edges` |
| `node`      | subgraph 内部的执行节点，代表一次具体的执行动作（如 LLM 推理、跨容器调用等） | `node_key`、`node_type`、`task_prompt`、`conditional_edges`、`input_schema_json` |
| `edge`      | 流转关系；container 级别的 edge 连接 subgraph，subgraph 级别的 edge 连接内部 node | `edge_type`、`condition_expr`、`config_json`                                    |

项目当前已固定的结构类型如下：

- **容器角色类型**：`human`、`agent`、`system`
- **subgraph 内执行节点类型**：`start`、`llm`、`handoff`、`invoke`、`end`
- **边类型**：`call`、`return`、`retry`（container 级）；`seq`（subgraph 内部顺序流转）

这意味着本方案中的 Agent，不应再只被理解为“抽象职责块”，而应被理解为：

1. **在运行时是独立职责主体**；
2. **在建模时是一个或多个 container 的候选承载对象**；
3. **在图上通过 node 表达内部执行阶段，通过 edge 表达协作关系**。

### 1.5 节点执行模型

执行节点（`node`）存在于 subgraph 内部，共五种类型：

| 类型      | 执行模型                                                                        | 完成信号                                   |
| --------- | ------------------------------------------------------------------------------- | ------------------------------------------ |
| `start`   | 透传，接收上游输入并注入当前节点上下文                                          | 直接流转，无推理过程                       |
| `llm`     | 三段式执行：`input`（增量上下文）→ `output`（结构化结果 ± tool call 列表）→ `tool call results`（若有）| 显式调用 `complete_phase` 后视为完成       |
| `handoff` | 将流程控制权交回 `human` 容器，挂起当前执行，等待用户确认或补充输入             | 用户输入到达，结果注入当前节点上下文后继续 |
| `invoke`  | 确定性跨容器调用，目标容器在配置中静态指定，payload 经 Sidebar 路由至目标容器   | `return` 边到达，结果注入当前节点上下文后继续 |
| `end`     | 透传，将 subgraph 最终输出返回给调用方                                          | 节点完成即 subgraph 完成                   |

> **注意**：执行节点是 subgraph 内部的概念。在拓扑图视图中，用户看到的是 subgraph（一个语义单元），subgraph 内部的节点序列在钻取时才可见。

#### llm 节点的三段式结构

每个 `llm` 节点的一次完整执行由三段组成：

| 阶段                | 内容                                                                                     |
| ------------------- | ---------------------------------------------------------------------------------------- |
| `input`             | 从前序执行上下文中**增量选取**的消息序列，由节点配置决定引入哪些结果（delta 上下文）     |
| `output`            | LLM 的输出，可能是纯结构化结果，也可能是结构化结果 + tool call 列表（一次性并行发起）    |
| `tool call results` | 若 `output` 含 tool call，则并行执行所有调用，将全部结果追加到本节点上下文后，节点完成   |

下一个节点的 `input` 从已有执行上下文中按需增量选取（delta），而不是默认传入全量历史，节点间通过增量上下文传递，保持上下文精简可控。

#### llm 节点的行为维度

`llm` 节点唯一的配置维度是**是否注入 tools**：

- **无 tools**：`output` 仅含结构化结果，无 tool call 列表，节点直接完成（适用于纯结构化推理、意图识别、结果汇总等）
- **有 tools**：`output` 可含 tool call 列表，并行执行后将 `tool call results` 追加到上下文，节点完成（适用于读 Actor、调用外部 API、跨容器委托等）

#### 典型场景映射

| 场景         | tools | 典型节点                                                                        |
| ------------ | ----- | ------------------------------------------------------------------------------- |
| 纯结构化推理 | 无    | `intent_parse`、`reply_compose`、`build_change_command`、`qa_pass_decision` |
| 工具调用     | 有    | `load_requirement_state`、`collect_requirement_set`、`delegate_to_agent`        |

#### handoff 节点

`handoff` 节点**只用于发起人工确认**，不用于跨 Agent 容器调用。运行时到达此节点时，流程挂起，将当前上下文交回 `human` 容器，等待用户输入或确认；用户响应到达后，结果注入本节点上下文，流程从此处继续。

#### invoke 节点

`invoke` 节点用于**确定性跨容器调用**，目标容器在节点配置中静态指定，不需要 LLM 推理决策。运行时到达此节点时，将当前 payload 投递给目标容器，由 Sidebar 路由到可用执行器；目标容器处理完成后通过 `return` 边回流结果，结果注入本节点上下文，流程继续。

与其他节点的区别：

| 节点 | 目标 | 是否挂起 | 路由方式 |
| --- | --- | --- | --- |
| `handoff` | `human` 容器 | 是，等用户输入 | 固定 |
| `invoke` | `agent` / `system` 容器 | 否，Sidebar 自动路由 | 配置中静态指定 |
| `llm` + tools | 任意（LLM 决定） | 否 | LLM 动态决策 |

使用 `invoke` 的判断标准：**目标容器已知且固定，且调用完成后还需继续执行后续节点**（如需求管理 Agent → Actor，写入完成后还要 `summarize_write_result`）。若容器处理完直接结束，用 `end` 节点触发 `return` 边回流即可，无需 `invoke`。若目标需要 LLM 根据上下文判断，仍使用注入了 tools 的 `llm` 节点。

#### 节点上下文管理规则

节点的输入上下文由 runtime 自动组装，不需要每个节点单独配置。

**默认规则**

runtime 沿拓扑图的入边，取直接前驱节点的 `output` 作为本节点的增量输入。任务载荷（`$task`，即调用方传入的委托指令）始终作为第一条消息注入，无需显式声明。

**tool call 结果的保留策略**

并非所有 tool call 的结果都需要传递给后续节点。每个 tool 在定义时声明 `context_mode`：

| context_mode | 含义 | 典型场景 |
| --- | --- | --- |
| `transparent` | 结果保留在节点上下文中，后续节点可见 | Actor Ask 读取需求状态 |
| `opaque` | 结果仅在本节点内消费，不向后传播 | 写入操作，后续只需知道成功/失败 |

runtime 根据 `context_mode` 自动决定是否将 tool_exchange 纳入后续节点的增量输入。

**可观测性要求**

由于上下文错误不会触发 LLM 报错（LLM 会基于错误上下文给出看似合理的结果），runtime 必须将每个节点实际收到的 `input_messages` 持久化到执行图记录中，供调试和审计使用。

### 1.6 Subgraph 子图

#### 定义

`subgraph` 是 container 的**子元素**，对应拓扑图中用户可见的**一个节点**。它代表一个有明确语义的执行单元，内部包含若干执行节点（`node`）和内部流转边，共同完成这一语义单元的所有步骤。

**核心映射关系**：拓扑图中的一个节点 = 执行图中的一个 subgraph。

层级关系：

```
graph
  └── container（agent 边界）
        ├── subgraph A（拓扑图中的节点 A，内含执行步骤）
        │     ├── node（执行步骤，如 llm / invoke）
        │     ├── node
        │     └── edge（subgraph 内部流转）
        ├── subgraph B（拓扑图中的节点 B）
        │     └── node
        └── edge（container 级别，连接 subgraph A → subgraph B）
```

#### 与 container 的核心区别

| 维度 | `container` | `subgraph` |
| --- | --- | --- |
| 层级 | 图的直接子元素 | container 的子元素 |
| 语义 | agent 的职责边界 | 一个语义单元（对应拓扑图的一个可见节点） |
| `role_type` | 有（`human` / `agent` / `system`） | 无 |
| 跨容器边 | 通过 `call` / `return` 边与其他容器通信 | 不参与跨容器通信，仅在所属 container 内部被引用 |
| 可复用 | 否 | 是（多个 container 可引用同一 subgraph 定义） |
| 拓扑图可见性 | 直接可见（一个矩形框） | 直接可见（框内的一个节点）；内部 node 在钻取时可见 |

#### 为什么需要 subgraph

在纯平铺节点模型中，拓扑图的"节点粒度"与"执行步骤粒度"是同一层次的，导致两个问题：

1. **语义粒度与执行粒度耦合**：一个逻辑步骤（如"获取所有需求信息"）被迫等价于一个 LLM 推理动作，无法表达内部有多步执行。
2. **拓扑图难以阅读**：执行细节和业务语义混在同一层，高层视图因为执行细节过多而失去可读性。

引入 subgraph 后：

- 拓扑图只展示 subgraph（业务语义节点），保持高层可读性
- subgraph 内部的执行步骤独立管理，可在不改变拓扑结构的情况下调整实现细节
- 跨 container 的 `call` / `return` 边仍连接 subgraph 层（表达 container 间协作），内部 node 序列只在 subgraph 范围内流转

#### 单步 subgraph 与多步 subgraph

subgraph 内部可以有任意数量的执行节点：

| subgraph 类型 | 内部节点数 | 典型场景 |
| --- | --- | --- |
| 单步 subgraph | 1 个 `llm` 节点 | 纯结构化推理，如意图识别、结果汇总 |
| 多步 subgraph | N 个节点 | 需要读 → 推理 → 调用等多个阶段，如批量读取需求状态 |

单步 subgraph 在结构上等价于原有的单节点，不引入额外开销；多步 subgraph 是新能力。

#### 典型多步 subgraph 示例

**`collect_requirement_set`**（冲突检测 Agent 中）

语义：批量获取一组需求的最新状态。拓扑图中显示为一个节点，内部展开为：

```
batch_ask_start (start)
  → parallel_actor_ask (llm, 有 tools，并行发出多个 Actor Ask)
  → aggregate_states (llm, 无 tools，聚合结果)
  → (end，输出给下一个 subgraph)
```

**`load_latest_requirement`**（质检 Agent 中）

语义：按 `min_version` 栅栏读取需求最新状态。内部展开为：

```
read_version (llm, 有 tools，Actor Ask 取当前版本号)
  → version_compare (llm, 无 tools，比对版本，通过/失败分支)
  → (end，输出给 qa_dimension_review subgraph)
```

### 1.7 Agent 方案与现有执行拓扑模板的对齐方式

为了与项目中已完成的执行图编辑器、结构构建器、校验器保持一致，建议本方案默认采用“**一类业务意图 → 一张拓扑模板 → 多个容器 + 多个节点**”的表达方式。

#### 建议映射原则

| 设计对象         | 建议映射                                                            |
| ---------------- | ------------------------------------------------------------------- |
| 用户输入         | 一个 `human` 容器，内部至少包含 `start` 与输入整理节点              |
| 会话总控 Agent   | 一个 `agent` 容器，内部通常包含意图识别、路由决策、结果聚合三个节点 |
| 专项 Agent       | 各自独立的 `agent` 容器，禁止共用同一职责容器                       |
| RequirementActor | 一个 `system` 容器，承接读写动作和状态校验                          |
| 自动重试         | 使用 `retry` 边表达，而不是把重试折叠到单个节点文案里               |
| 人工澄清/挂起    | 使用 `handoff` 节点表达“从系统流转回用户”的转交点                   |

#### 为什么要这样对齐

- 这样能直接复用当前项目已经完成的图编辑、保存、预览和结构校验能力。
- 这样能把“流程编排责任”与“节点内部推理责任”清晰分离。
- 这样未来在 Sidebar 自动注入 `span`、自动生成跨容器边时，不需要推翻现有模板模型。
- 这样能够自然承接后续的运行时执行图、Checkpoint 与恢复机制。

### 1.8 执行流程的状态与重试机制

每条用户指令在运行时都对应一张执行图，动态记录完整执行过程。最终状态三选一：

- `Succeeded`：流程正常结束
- `Failed`：无法恢复的错误
- `Suspended`：等待用户补充输入后恢复

**质检失败重试**：质检 Agent 返回不通过时，会话总控将质检结论作为新约束重新委托需求管理 Agent，执行图中产生 `retry` 边。重试上限为 **3 次**，超限后执行图置为 `Suspended`，向用户说明卡滞的质检项与原因。

**Actor 校验失败**：若需求当前状态不允许写入（如已基线锁定），则该错误不应走自动重试，而应直接回到会话总控，由会话总控决定转为用户澄清或变更流程。

**挂起恢复**：当用户补充输入后，不创建“全新流程替代旧流程”，而是在原运行链路上继续追加新的输入节点和恢复边，保证一次用户意图的完整可追溯性。

### 1.9 设计原则

1. **单一职责**：每个 Agent 只做一种类型的判断或操作。
2. **会话总控统一编排**：所有专项 Agent 的协作必须通过会话总控完成。
3. **Actor 唯一权威写入口**：所有业务状态修改都必须经由 `RequirementActor`。
4. **强一致读取优先**：推理决策依赖的数据必须以 Actor Ask 为准。
5. **图模型优先表达**：凡是已经能用容器、节点、边表达的流程语义，不再埋入自然语言约定。
6. **模板先于运行**：先把可复用流程建成拓扑模板，再逐步打通运行时自动追踪。
7. **container 是 agent 边界，subgraph 是语义单元**：container 包含 subgraph，subgraph 对应拓扑图中的一个可见节点；不得用 container 承担步骤分组职责，subgraph 也不跨越 container 边界通信。

## 二、Agent 全览

| Agent          | 所在层 | 核心职责                     | 是否可写 RequirementActor | 典型触发                      | 在执行图中的建议承载                    |
| -------------- | ------ | ---------------------------- | ------------------------- | ----------------------------- | --------------------------------------- |
| 会话总控 Agent | 会话层 | 意图识别、流程编排、结果汇总 | 否                        | 所有用户输入                  | 单独 `agent` 容器                       |
| 需求管理 Agent | 执行层 | 需求创建、修改、补全、重写   | 是                        | 新建/修改/补充需求            | 单独 `agent` 容器 + Actor `system` 容器 |
| 质检 Agent     | 执行层 | 对单条需求做结构化评估       | 否                        | 修改后自动质检 / 用户主动质检 | 单独 `agent` 容器                       |
| 冲突检测 Agent | 执行层 | 对多需求间冲突做语义裁决     | 否                        | 用户主动触发 / 变更后可选触发 | 单独 `agent` 容器                       |

从执行图角度看，四类 Agent 的关系不是“谁调用谁的代码”，而是“谁在什么节点上接棒、谁对什么数据负责、谁通过何种边进入下一阶段”。

## 三、各 Agent 详细设计

### 3.1 会话总控 Agent

#### 职责边界

会话总控 Agent 是唯一面向用户的 Agent，职责只包括：

- 识别用户当前意图属于哪一类需求操作
- 决定应委托给哪个专项 Agent
- 编排多步骤流程顺序
- 聚合多个 Agent 的返回结论并回复用户

它**不直接修改需求内容**，也**不对需求质量或冲突做专业裁决**。

#### 核心能力

- **意图识别**：区分创建、修改、质检、冲突检测、复合意图等类型
- **对象识别**：识别目标需求 ID、项目范围、上下文引用对象
- **流程编排**：对复合意图拆分步骤，按依赖顺序委托
- **异常分流**：区分可自动重试、需挂起澄清、可直接失败返回的场景
- **结果聚合**：把结构化结果转成面向用户的自然语言反馈

#### 典型决策逻辑

```
收到用户输入
  ├── 识别意图类型
  ├── 若为单步意图 → 直接委托对应专项 Agent
  ├── 若为复合意图 → 拆解为步骤序列
  │      ├── 修改需求
  │      ├── 触发质检
  │      └── （可选）触发冲突检测
  ├── 收集各步骤返回结果
  └── 汇总为用户回复
```

#### 在执行图中的映射

会话总控 Agent 建议始终建模为独立容器，内部至少包含以下节点：

| 节点建议           | 节点类型 | 配置特征            | 作用                                 |
| ------------------ | -------- | ------------------- | ------------------------------------ |
| `session_start`    | `start`  | —                   | 接收当前轮用户输入                   |
| `intent_parse`      | `llm`    | 无 tools | 将自然语言转为结构化意图                         |
| `delegate_to_agent` | `llm`    | 有 tools | 通过 tool call 发起跨容器委托，等待 tool result 回流 |
| `reply_compose`     | `llm`    | 无 tools | 聚合下游结果并生成自然语言回复                   |
| `session_end`      | `end`    | —                   | 完成该次指令处理                     |

其中：

- `delegate_to_agent` 是一个注入了 tools 的 `llm` 节点，持有各专项 Agent 的调用工具（`invoke_requirements_agent` / `invoke_qa_agent` / `invoke_conflict_agent`），通过 tool call 发起委托，tool result 即为下游返回结论；
- 在执行图中，跨容器调用仍用 `call` 边、`return` 边表达，由 Sidebar 在 tool call 发出和结果回流时自动写入；
- 当路由失败或需用户澄清时，可从 `route_decision` 连到面向用户的 `handoff` 节点。

#### 输入 / 输出

- **输入**：用户自然语言 + 当前会话上下文
- **输出**：结构化委托指令，或最终面向用户的回复内容

### 3.2 需求管理 Agent

#### 职责边界

需求管理 Agent 是唯一负责**写入需求状态**的专项 Agent。它负责将用户或上游流程给出的变更目标转化为结构化修改动作，并经由 `RequirementActor` 落地。

它的职责包括：

- 创建新需求
- 修改需求描述、验收标准、优先级等字段
- 根据质检反馈对需求进行重写或补全
- 在写入前后与 Actor 交互，获取最新状态与版本

它**不负责最终质量评判**，也**不负责跨需求冲突裁决**。

#### 核心能力

- **变更理解**：将用户语言中的修改意图解析成结构化变更项
- **状态预读**：在写入前通过 Actor Ask 获取目标需求最新状态
- **命令构造**：生成规范化写 Command 提交给 `RequirementActor`
- **结果归纳**：把写入结果、版本号、修改摘要回传给会话总控

#### 典型决策逻辑

```
收到需求修改委托
  ├── 读取目标需求最新状态（Actor Ask）
  ├── 判断当前状态是否允许修改
  │     ├── 不允许 → 返回失败原因
  │     └── 允许 → 构造写 Command
  ├── 提交给 RequirementActor
  ├── 获取写入结果（成功 / 校验失败）
  └── 返回修改摘要 + 最新版本号
```

#### 在执行图中的映射

需求管理 Agent 与 `RequirementActor` 最适合表达为两个相邻容器：

| 容器                           | `role_type` | 说明                     |
| ------------------------------ | ----------- | ------------------------ |
| `requirements_agent_container` | `agent`     | 理解修改意图、形成命令   |
| `requirement_actor_container`  | `system`    | 负责校验、写入、版本推进 |

需求管理 Agent 容器内部建议节点：

| 节点建议                 | 节点类型 | 配置特征            | 作用                                |
| ------------------------ | -------- | ------------------- | ----------------------------------- |
| `requirements_start`     | `start`  | —                   | 接收委托                            |
| `load_requirement_state` | `llm`    | 有 tools | 调用 Actor Ask 读取当前需求最新状态 |
| `build_change_command`   | `llm`    | 无 tools | 将修改意图转为结构化写命令          |
| `write_invoke`           | `invoke` | 目标：Actor 容器    | 向 Actor 发起写入，等待写入结果回流 |
| `summarize_write_result` | `llm`    | 无 tools | 总结变更结果与版本信息              |
| `requirements_end`       | `end`    | —                   | 结束                                |

Actor 容器内部建议节点：

| 节点建议                | 节点类型 | 配置特征            | 作用               |
| ----------------------- | -------- | ------------------- | ------------------ |
| `actor_receive_command` | `start`  | —                   | 接收 Command       |
| `actor_validate_state`  | `llm`    | 无 tools | 校验状态与约束     |
| `actor_apply_event`     | `llm`    | 有 tools | 写入事件并推进版本 |
| `actor_return_result`   | `end`    | —                   | 返回结果           |

跨容器边建议：

- 需求管理 Agent → Actor：`call`
- Actor → 需求管理 Agent：`return`
- 需求管理 Agent → 质检 Agent：由会话总控发起，不直接相连

#### 输入 / 输出

- **输入**：目标需求 ID + 修改意图 + 可选约束（如质检反馈）
- **输出**：修改摘要 + 最新版本号 + 写入结果

### 3.3 质检 Agent

#### 职责边界

质检 Agent 负责对**单条需求**做结构化质量评判，判断其是否达到预期标准。它只读、不写。

质检对象可以包括：

- 描述是否清晰
- 验收标准是否可测试
- 层级拆分是否合理
- 字段间是否自洽

它的输出不是“帮用户直接修改”，而是“给出是否通过、问题定位、可重试约束”。

#### 核心能力

- **强一致读取**：读取目标需求最新版本状态
- **多维度评审**：从完整性、明确性、可测试性、一致性等维度打分或判定
- **问题定位**：指出不通过的字段、段落或语义缺陷
- **重试约束生成**：把评审意见转成可供需求管理 Agent 使用的修改约束

#### 典型决策逻辑

```
收到质检委托（目标需求 ID + min_version）
  ├── 向 Actor 直读最新状态（Actor Ask）
  ├── 校验版本是否达到最低要求
  ├── 按各质检维度逐一评判
  ├── 全部通过 → 返回通过结论
  └── 存在不通过项
        ├── 生成问题定位 + 重试约束
        └── 返回不通过结论（含各维度详情）
```

#### 与需求管理 Agent 的协作模式

质检 Agent 与需求管理 Agent 之间不直接通信，**始终通过会话总控中转**。典型重试路径：

```
质检 Agent 返回不通过结论
  → 会话总控判断是否在重试上限内（上限 3 次）
  → 未超限：将质检结论作为新约束重新委托需求管理 Agent
  → 超限：向用户说明卡滞原因，执行图置为 Suspended
```

#### 在执行图中的映射

质检 Agent 容器内部建议节点：

以下每行对应拓扑图中的**一个 subgraph**（可见节点）：

| subgraph 建议             | 内部执行节点数 | 作用                                         |
| ------------------------- | -------------- | -------------------------------------------- |
| `qa_start`                | 1（`start`）   | 接收质检委托                                 |
| `load_latest_requirement` | 多步（`read_version` → `version_compare`） | 按 `min_version` 栅栏读取需求最新状态 |
| `qa_dimension_review`     | 1（`llm`，无 tools） | 对多个维度展开结构化评审               |
| `qa_pass_decision`        | 1（`llm`，无 tools） | 判断是否通过，输出结构化质检结论       |
| `qa_end`                  | 1（`end`）     | 结束，结论经 `return` 边自动回流会话总控     |

与其他容器的边建议：

- 会话总控 → 质检 Agent：`call`
- 质检 Agent → 会话总控：`return`
- 质检 Agent 不应直接连到需求管理 Agent
- 若表达自动重试，可由会话总控容器中的决策节点连出一条 `retry` 边回到需求管理 Agent 容器

#### 输入 / 输出

- **输入**：目标需求 ID + 期望的最低版本号（用于版本栅栏）
- **输出**：结构化质检结论（各维度通过状态 + 问题定位 + 重试约束）

### 3.4 冲突检测 Agent

#### 职责边界

冲突检测 Agent 对**多条需求之间**进行语义层面的冲突分析，做出最终的冲突裁决。它**不修改任何需求**，只输出冲突报告供用户或后续流程参考。

冲突类型定义：

| 冲突类型   | 说明                                                       |
| ---------- | ---------------------------------------------------------- |
| 逻辑冲突   | 两条需求的约束条件或验收标准在逻辑上互斥                   |
| 优先级冲突 | 同一资源或目标在不同需求中被赋予不兼容的优先级             |
| 范围重叠   | 两条需求的功能边界存在模糊重叠，可能导致重复实现或实现空白 |

#### 核心能力

- **分析范围确定**：根据用户指令确定参与检测的需求集合（指定范围 / 项目全量 / 最近变更集）
- **候选冲突识别**：对需求两两组合做粗筛，识别存在潜在冲突可能的候选对
- **语义裁决**：对候选冲突对逐一做精细语义分析，判断是否确实构成冲突、冲突类型及严重程度
- **结论结构化输出**：冲突报告中每条记录包含涉及的需求 ID、冲突类型、冲突描述及建议处理方向

#### 典型决策逻辑

```
收到冲突检测委托（需求 ID 列表 / 项目 ID）
  ├── 向 Actor 直读各需求最新状态（Actor Ask）
  ├── 生成候选冲突对列表（两两比对）
  ├── 对每个候选对做语义裁决
  │     ├── 确认冲突 → 记录冲突类型 + 严重程度 + 描述
  │     └── 排除冲突 → 跳过
  └── 返回冲突报告（含冲突总数、各冲突详情）
```

#### 触发时机

冲突检测 Agent 有两种触发路径：

1. **用户主动触发**：用户明确要求检查冲突，会话总控直接委托。
2. **需求修改后自动触发**（可选）：需求管理 Agent 完成写入且质检通过后，会话总控可选择性地触发冲突检测，检测范围为与被修改需求存在关联的周边需求。

#### 在执行图中的映射

冲突检测 Agent 容器内部建议节点：

以下每行对应拓扑图中的**一个 subgraph**（可见节点）：

| subgraph 建议             | 内部执行节点数 | 作用                                   |
| ------------------------- | -------------- | -------------------------------------- |
| `conflict_start`          | 1（`start`）   | 接收检测委托                           |
| `collect_requirement_set` | 多步（`batch_ask_start` → `parallel_actor_ask` → `aggregate_states`） | 批量 Actor Ask，读取所有目标需求最新状态 |
| `build_conflict_pairs`    | 1（`llm`，无 tools） | 生成候选冲突对列表               |
| `conflict_adjudication`   | 1（`llm`，无 tools） | 对候选对做语义裁决，输出结构化冲突报告 |
| `conflict_end`            | 1（`end`）     | 结束，报告经 `return` 边自动回流会话总控 |

如果未来需要支持“冲突后建议修复”，应新增新的专项 Agent，而不是让冲突检测 Agent 兼任写入职责。

#### 输入 / 输出

- **输入**：需求 ID 列表或项目 ID（全量检测）
- **输出**：结构化冲突报告（冲突总数 + 各冲突条目详情）

## 四、基于现有执行图能力的模板化建模建议

### 4.1 模板一：修改需求 + 自动质检

这是当前 Agent 方案最核心、最适合优先沉淀为拓扑模板的路径。

#### 建议容器划分

| 容器键               | 角色类型 | 说明               |
| -------------------- | -------- | ------------------ |
| `human_input`        | `human`  | 用户提出修改意图   |
| `conductor`          | `agent`  | 会话总控编排       |
| `requirements_agent` | `agent`  | 负责形成修改命令   |
| `requirement_actor`  | `system` | 落地写入与版本校验 |
| `qa_agent`           | `agent`  | 质检与重试反馈     |

#### 建议边关系

| 源 → 目标                                  | 边类型   | 说明                   |
| ------------------------------------------ | -------- | ---------------------- |
| `human_input` → `conductor`                | `call`   | 用户输入进入编排层     |
| `conductor` → `requirements_agent`         | `call`   | 委托修改               |
| `requirements_agent` → `requirement_actor` | `call`   | 发起写入               |
| `requirement_actor` → `requirements_agent` | `return` | 返回写入结果与版本     |
| `requirements_agent` → `conductor`         | `return` | 返回修改摘要           |
| `conductor` → `qa_agent`                   | `call`   | 触发质检               |
| `qa_agent` → `conductor`                   | `return` | 返回质检结论           |
| `conductor` → `requirements_agent`         | `retry`  | 质检不通过时按约束重试 |

#### 推荐的 `config_json` 约定

| 边类型   | 建议配置                                           |
| -------- | -------------------------------------------------- |
| `call`   | `param_mapping`：将上游输出映射到下游输入          |
| `return` | `result_mapping`：将结果映射回调用方上下文         |
| `retry`  | `max_retries`、`retry_delay_ms`、`retry_on_errors` |

例如：

```json
{
  "param_mapping": {
    "requirement_id": "target_requirement_id",
    "change_summary": "change_request_text"
  }
}
```

```json
{
  "max_retries": 3,
  "retry_delay_ms": 0,
  "retry_on_errors": ["qa_not_passed"]
}
```

### 4.2 模板二：修改需求 + 质检通过后检查冲突

当用户请求“先改，再看有没有冲突”时，建议在模板层建模为串联路径，而不是在会话总控内部隐式约定。

建议路径：

```
human_input
  → conductor
  → requirements_agent
  → requirement_actor
  → conductor
  → qa_agent
  → conductor
  → conflict_agent
  → conductor
```

其中会话总控容器中的决策节点可以表达：

- 质检未通过：回到需求管理 Agent（`retry`）
- 质检通过：进入冲突检测 Agent（`call`）
- 用户未要求冲突检测：直接结束

### 4.3 模板三：需要用户澄清的挂起路径

当系统无法继续自动推进时，应在模板中显式预留“转交给用户”的 handoff 节点。

建议表达：

```
conductor.delegate_to_agent
  ├── 信息充分 → 下游专项 Agent
  └── 信息不足 → clarification_handoff → human_input_reentry
```

这类路径虽然当前尚未与运行时恢复机制完全打通，但提前在模板中表达清楚，可以避免未来执行图能力补齐时重建模型。

### 4.4 节点粒度建议

为了兼顾可观测性与可维护性，建议节点粒度遵循以下原则：

| 场景                      | 建议粒度                                                                       |
| ------------------------- | ------------------------------------------------------------------------------ |
| 纯结构化推理，无外部调用  | 单步 subgraph（内含 1 个 `llm` 节点，无 tools）                                |
| 需要调用 Actor / 外部 API | 单步 subgraph（内含 1 个 `llm` 节点，有 tools，一次性并行发出所有 tool call）  |
| 需要跨容器调用 Agent/Actor | 单步 subgraph（内含 1 个 `invoke` 节点，目标容器静态指定）                     |
| 需要人工确认或补充输入    | 单步 subgraph（内含 1 个 `handoff` 节点）                                      |
| 需要自动重试              | container 级 `retry` 边，连接两个 subgraph                                     |
| 需要跨角色切换            | 拆 container，不要在一个 container 内混用 `role_type`                          |
| 一个语义步骤需要多步执行（读→推理→写等） | 多步 subgraph（内含多个执行节点，`seq` 边连接） |

### 4.5 多步 Subgraph 定义示例

以下是推荐沉淀为可复用 subgraph 定义的高频序列：

#### `collect_requirement_set`（冲突检测 Agent）

批量读取一组需求的最新状态。

| 内部执行节点        | 节点类型 | 作用                                    |
| ------------------- | -------- | --------------------------------------- |
| `batch_ask_start`   | `start`  | 接收需求 ID 列表                        |
| `parallel_actor_ask`| `llm`    | 有 tools，并行发出多个 Actor Ask        |
| `aggregate_states`  | `llm`    | 无 tools，聚合所有返回结果为统一结构    |

#### `load_latest_requirement`（质检 Agent）

按 `min_version` 栅栏读取需求最新状态。

| 内部执行节点        | 节点类型 | 作用                                      |
| ------------------- | -------- | ----------------------------------------- |
| `read_version`      | `llm`    | 有 tools，Actor Ask 取当前版本号          |
| `version_compare`   | `llm`    | 无 tools，比对版本，输出 pass / fail 分支 |

## 五、协作流程示例

### 示例一：修改需求 + 自动质检

```
用户：“把需求 #42 的验收标准改得更具体”

会话总控
  └─→ 需求管理 Agent（修改 #42 验收标准）
        └─→ RequirementActor → 写入成功，version=7
  └─→ 质检 Agent（检查 #42，min_version=7）
        ├── 通过 → 回复用户“修改完成，质检通过”
        └── 不通过（如：验收标准仍不可测试）
              → 重新委托需求管理 Agent（附带质检约束）
              → 最多循环 3 次
              → 3 次仍不通过 → 向用户说明问题，挂起等待
```

对应的执行图建模重点：

- 会话总控到需求管理 Agent：`call`
- 需求管理 Agent 到 Actor：`call`
- Actor 返回需求管理 Agent：`return`
- 会话总控到质检 Agent：`call`
- 质检不通过回需求管理 Agent：由会话总控发出 `retry`

### 示例二：修改后检查冲突

```
用户：“修改需求 #42 的优先级为最高，然后看看有没有冲突”

会话总控（识别为复合意图，拆分为两步）
  └─→ Step 1：需求管理 Agent（修改 #42 优先级）→ 成功，version=8
  └─→ Step 2：冲突检测 Agent（检测与 #42 相关的需求）
        └─→ 返回冲突报告
会话总控 → 将两步结论合并回复用户
```

对应的执行图建模重点：

- 会话总控容器中应有一个含 `branch` 字段的 `llm` 节点，决定是否进入冲突检测路径。
- 冲突检测不应与需求管理 Agent 直接相连，而应通过会话总控衔接。

### 示例三：Actor 校验失败

```
用户：“修改需求 #42 的描述”

需求管理 Agent → RequirementActor
  Actor 校验失败（#42 处于 Baselined 状态，不允许直接修改）
  └─→ 返回失败原因 → 上报会话总控

会话总控 → 告知用户“该需求已基线锁定，如需修改需先发起变更流程”
执行图置为 Suspended，等待用户决策
```

对应的执行图建模重点：

- 这是“业务约束失败”，不是“可自动重试失败”。
- 因此不应从会话总控连出 `retry` 边，而应进入 `handoff` 节点或挂起路径。

## 七、Sidebar 通信中间件设计

### 7.1 核心职责

Sidebar 是跨容器调用的**抽象层**。本方案中 Agent 是执行图里的静态定义（container + subgraph + node），内存中不存在 Agent 实例，也不存在需要心跳维护的常驻进程。Sidebar 的职责因此精确限定为：**接收 tool call、找到对应容器入口、投递 payload、路由结果回来**。

具体职责：

- **工具调度（Tool-Call Dispatch）**：接收会话总控发出的 tool call，按工具名找到对应的 container 执行入口，将 payload 投递进去，并将结果路由回发起节点的 tool result
- **消息追踪**：自动为跨容器调用生成执行图边（`call`、`return`、`retry`）
- **超时与失败处理**：处理通信级调用超时，定义明确的失败语义

Sidebar **不做健康检查、不做负载均衡**——Agent 是静态图定义，不是进程实例，不存在”实例健康”或”实例过载”的概念。

### 7.2 通信模型

```
┌─────────────────────────────────────────────────────────────┐
│                     会话总控 Agent                          │
│   （调用已注入工具：invoke_qa_agent(payload)）              │
│   （不感知执行图内部结构，只知道工具名与其语义）            │
└──────────────────────┬──────────────────────────────────────┘
                       │  tool call（具名工具）
                       ▼
         ┌──────────────────────────┐
         │    Sidebar 调度层        │
         │  ┌──────────────────┐   │
         │  │ 工具名 → 容器入口│   │
         │  │ tool_name → entry│   │
         │  └──────────────────┘   │
         └────────────┬────────────┘
                      │ 投递到对应 container 的 start 节点
                      ▼
         ┌──────────────────────────┐
         │  质检 Agent container    │
         │  qa_start                │
         │    → load_latest_req     │
         │    → qa_dimension_review │
         │    → qa_pass_decision    │
         │    → qa_end（return）    │
         └──────────────────────────┘
                      │  结果经 return 边回流
                      ▼
              会话总控 tool result
```

工具名到容器入口的映射在系统初始化时静态确定，运行时不做动态匹配。

### 7.3 Tool-Call Dispatch 机制

dispatch 流程：

```
会话总控 llm 节点发起 tool call（如 invoke_qa_agent(payload)）
  → Sidebar 接收 tool call
  → 查工具名 → container 映射，定位 qa_agent_container 的 start 节点
  → 将 payload 投递到该节点
  → container 内部节点序列依次执行
  → end 节点触发 return，结果路由回会话总控的 tool result
  → 会话总控继续推理
```

Sidebar 的决策约束：

- **静态映射**：工具名到容器入口的映射启动时固定，无运行时动态匹配
- **失败语义显式**：执行失败或超时时，明确定义返回内容，不留给调用方猜测
- **结果路由保证**：tool result 必须回到发起该 tool call 的节点上下文，不能跨会话混淆

### 7.4 消息传递协议

跨容器消息的信封语义，至少包含以下几类信息：

- **关联上下文**：`session_id`、`graph_id`，用于关联所属会话与执行图
- **路由语义**：调用方容器、目标容器、优先级与时限约束
- **业务载荷**：本次协作需要处理的业务内容
- **追踪元数据**：用于生成执行图边、记录调用因果、支撑审计与回放

核心原则：**业务 payload 与路由/追踪元数据分层**，前者服务于 Agent 处理任务，后者服务于系统编排与观测，二者不相互污染。

### 7.5 超时与失败策略

| 场景                 | 负责层           | 处理原则                                   |
| -------------------- | ---------------- | ------------------------------------------ |
| 网络抖动、通信级超时 | Sidebar          | 有限重试，超限后返回明确失败               |
| 质检不通过           | 会话总控         | 业务闭环的一部分，由编排层决定是否重试     |
| Actor 校验失败       | 会话总控 / Actor | 业务约束失败，不应由 Sidebar 自动重试      |

Sidebar 只负责”通信级失败”；业务语义上的重新编排和用户澄清，仍属于会话总控职责。

### 7.6 执行图边自动生成

Sidebar 负责把跨容器协作沉淀为可追踪的执行事实：

- 请求路由时写入 `call` 边
- 结果回流时写入 `return` 边
- 通信级重试时写入 `retry` 边

边只记录容器间协作事实，不替代各容器内部的节点执行状态。Sidebar 是”跨容器协作事实”的生产者，不是”业务节点内部行为”的解释器。

### 7.7 与现有通信层的集成

项目已有 Agent 通信基础设施（`backend_business/services/agent/messaging/`），Sidebar 作为路由层在其之上实现：

```
现有架构：
┌─────────────┐
│ MessageBus  │  底层消息传输
└──────┬──────┘
       ▼
┌─────────────┐
│   Agent     │  各 Agent container
└─────────────┘

Sidebar 集成后：
┌─────────────┐
│ MessageBus  │  底层消息传输（保留）
└──────┬──────┘
       ▼
┌─────────────┐
│  Sidebar    │  路由层（新增）
│  - 工具→容器映射 │
│  - 消息追踪与边生成 │
└──────┬──────┘
       ▼
┌─────────────┐
│   Agent     │  各 Agent container（不变）
└─────────────┘
```

集成原则：

1. **保留现有 MessageBus**：继续作为底层传输机制，不重新造消息基础设施
2. **Sidebar 只增加路由与追踪**：不侵入各 Agent container 的业务职责
3. **支持渐进切换**：按链路或按环境逐步启用，不一次性替换所有调用路径

### 7.8 部署约束

- **可开关**：是否启用 Sidebar 是可控的发布策略，而非硬编码前提
- **可回退**：路由层异常时有明确的降级路径与失败语义
- **可对账**：路由决策与执行图追踪能相互校验

### 7.9 监控与可观测性

Sidebar 需要能回答以下问题：

- **有没有正确路由**：tool call 最终进入了哪个容器入口
- **有没有异常扩散**：超时或失败是否导致整条调用链级联失败
- **有没有可追溯证据**：能否把 tool call、执行图边和最终结果串成完整链路

监控体系至少覆盖路由延迟、成功率、重试率以及跨容器调用链路追踪。

## 八、执行状态管理

Agent 在本方案中是执行图里的静态定义，内存中不存在 Agent 实例，也没有需要注册、心跳或崩溃恢复的常驻进程。需要管理的是**执行图的运行状态**：每条用户指令对应一张执行图，其状态随节点推进而变化，持久化在执行图存储中。

### 8.1 执行图状态

```
Running（节点序列推进中）
  ↓
Waiting（等待跨容器调用结果）← 结果到达 → 继续 Running
  ↓
Suspended（等待用户补充输入）← 用户输入 → 继续 Running
  ↓
Succeeded / Failed
```

| 状态        | 含义                           | 触发条件                                     |
| ----------- | ------------------------------ | -------------------------------------------- |
| `Running`   | 节点序列正在推进               | 执行图启动 / Waiting 结果到达 / Suspended 用户输入到达 |
| `Waiting`   | 某节点等待跨容器调用结果返回   | invoke 节点或 tool call 已发出，return 尚未到达 |
| `Suspended` | 整条流程等待用户补充输入       | 重试耗尽 / Actor 校验失败 / handoff 节点触发 |
| `Succeeded` | 执行图正常结束                 | end 节点完成                                 |
| `Failed`    | 发生不可恢复错误               | 执行异常且无法恢复                           |

### 8.2 Waiting 状态与 Checkpoint

节点进入 `Waiting` 时，运行时写入一条轻量 **Checkpoint** 记录：

- 所属 `graph_id`
- 进入等待的时间点
- 等待的 `task_id` 列表（并行调用时可能有多个）

Checkpoint **不存储中间推理状态**。所有节点的 input + output 已全量持久化于执行图存储中。结果到达时，运行时按 `graph_id` 从执行图中重建完整上下文，定位到挂起节点后继续执行。Checkpoint 只作为"还在等哪些任务"的查找索引。

并行等待场景下，运行时维护 pending task 计数器。计数归零时，将所有返回结果合并后一并注入下一个节点的 `input.messages`，触发推理继续。

### 8.3 Suspended 状态与恢复

`Suspended` 与 `Waiting` 的核心区别：`Waiting` 等待系统内部的异步结果，`Suspended` 等待用户的外部输入。

用户补充输入后：

- **不创建新的执行图**，在原执行图上追加新的输入节点
- 新输入作为增量 `messages` 注入到挂起节点序列末尾
- 运行时按节点序列重建完整上下文后继续执行
- 执行图状态从 `Suspended` 恢复为 `Running`

一次用户意图始终对应同一张执行图，中间的挂起、补充、恢复都完整可追溯。

### 8.4 执行状态的管理边界

| 职责                     | 负责方                       |
| ------------------------ | ---------------------------- |
| 执行图状态推进           | 运行时框架                   |
| Checkpoint 写入与查找    | 运行时框架                   |
| 上下文重建（按 graph_id）| 运行时框架（基于执行图存储） |
| 业务推理与决策           | 各 Agent container 内的节点  |
| 跨容器调用路由           | Sidebar                      |

## 九、并发模型与会话隔离

### 9.1 并发场景说明

系统中存在两类并发需要分别处理：

**跨会话并发**：多个用户同时发起请求，每个请求都需要独立的会话总控推理和执行图。

**会话内并发**：同一个会话的某个步骤中，Agent 同时向多个下游发起调用（如同时触发质检和冲突检测），多个结果需要汇合后才能继续。

### 9.2 跨会话隔离

每条用户指令对应唯一一张执行图（`graph_id`）。Agent 是静态图定义，不在内存中持有任何跨执行图的状态；所有推理上下文——节点序列、每轮的 input 与 output——都以 `graph_id` 为索引持久化在执行图存储中。不同会话的执行图天然独立，隔离是执行图模型的内在属性，不需要额外的隔离机制。

跨会话并发需要关注以下两点：

**数据读取**：Agent 通过 Actor Ask 读取需求数据时，返回特定 `requirement_id` 的最新状态，天然按业务实体隔离，无需会话级锁。

**写入串行化**：`RequirementActor` 对同一 `requirement_id` 的写命令串行处理，不同会话并发写同一需求时，命令依次进入 Actor 命令队列，后到的命令基于已更新的最新状态做前置校验。

### 9.3 会话内并发汇合

当会话总控在一个推理节点中同时发起多个下游调用时（如同时委托需求管理 Agent 和冲突检测 Agent），运行时通过以下机制保证汇合：

1. 发起调用时，为本次并行批次创建 pending task 计数器，初始值为并行任务数
2. 每个下游任务返回时，计数器减一，结果写入当前节点的待汇合缓冲区
3. 计数归零时，将所有结果合并为下一个节点的 `input.messages`，触发下一轮推理
4. 任意一个并行任务超时或失败，视配置决定是等待其余任务完成后统一上报，还是立即中断整批

在执行图中，多条返回边收敛到调用方 AgentContainer 的同一个汇合节点，这是并行调用在图结构上的自然表达，无需引入新的边类型。

### 9.4 会话总控自身的并发

会话总控是系统唯一面向用户的入口。每个用户会话对应独立的执行图，会话总控 container 在该执行图中推进节点序列。多个用户并发时，各自的执行图互相独立、互不干扰。

会话总控不在内存中积累跨轮次状态；当用户在同一会话中发出多轮指令时，后续指令通过执行图追加新节点继续推进，而非依赖内存中的"上下文记忆"。

### 9.5 专项 Agent 的无状态保证

需求管理 Agent、质检 Agent、冲突检测 Agent 三者是严格无状态的静态图定义：

- 每次任务所需的全部上下文通过调用方传入的消息 payload 完整携带，执行图存储所有上下文信息
- 任务完成后不在任何内存位置保留业务数据
- 来自不同会话的并发执行图互不干扰，隔离由执行图模型本身保证

## 十、后续扩展预留

现阶段四个 Agent 已能覆盖需求的创建、修改、质检和冲突检测的基本闭环。后续可按需引入：

- **计划 Agent**：当指令复杂度超出现有拓扑模板时，动态拆解执行路径。
- **评审 Agent**：将自然语言评审意见解析为结构化变更动作。
- **追溯 Agent**：上下游需求关联关系的语义推断与覆盖性分析。
- **执行图自动写入**：由 Sidebar 在调用链上自动写入 `call`、`return`、`retry` 边。
- **Checkpoint 恢复机制**：让 `Suspended` 的流程在用户补充输入后从挂起点恢复。
- **模板注入机制**：由会话总控在识别意图后自动匹配并装载拓扑模板。

从演进顺序上，建议优先做三件事：

1. 先把“修改需求 + 自动质检”沉淀为标准模板；
2. 再把会话总控与专项 Agent 的调用边自动写入执行图；
3. 最后补齐挂起恢复与运行时状态推进。
