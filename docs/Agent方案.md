# 引言

需求工程是软件研发中链路最长、协作摩擦最多的环节之一。在传统的人工协作模式下，需求的创建、修改、质检与冲突裁决分属不同角色。例如，产品经理负责撰写与变更，评审会议承担质量把关，资深成员凭经验识别跨需求矛盾。这一模式的固有问题在于：信息流转依赖人工传递，质检介入时机滞后，冲突往往在实现阶段才被发现，且整个过程难以被系统性追踪和复现。当需求规模增大或迭代频率加快时，人工协作的响应延迟与遗漏风险会成倍放大。

引入AI辅助是自然的演进方向，但传统的单体式AI助手在面对这类任务时，既要理解用户意图、又要判断质量、还要负责写入状态，职责混杂、行为难以预测，也很难在出错时精确定位问题根源。更深层的问题在于，随着需求数量增多、对话轮次积累，单体AI的上下文窗口会同时承载意图理解、领域知识、历史操作记录与当前状态，信息密度持续攀升，模型的注意力随之分散，早期的约束或决策容易被后续内容覆盖，导致行为漂移和前后矛盾。本质上，这只是把人工操作平移到了AI，并未改变协作结构本身，上下文的膨胀反而引入了人工模式中不存在的新风险。下图展示了模型的准确度随上下文增加而导致的准确度下降情况

本方案提出一套面向需求工程的多Agent协作架构**，**核心出发点是：把"理解意图"、"执行变更"、"评判质量"和"检测冲突"等视为本质上不同的任务，由各司其职的Agent承担不同的任务，再通过统一的编排层协同完成完整流程。这与人工协作中角色分工的直觉一致，但在响应速度、执行一致性和全程可追溯性上有本质提升：质检不再是事后会议，而是每次变更后的自动环节；冲突检测不再依赖个人经验，而是结构化的跨需求语义分析；每一步操作的上下文、版本与决策依据都沉淀在执行图中，可回溯、可审计。

# 架构总览

## 总体架构设计

本系统采用四层架构，自上而下依次为会话层、执行层、领域层与数据底座，各层职责严格隔离，层间通过明确定义的接口交互，不存在跨层直接调用。

会话层是用户与系统之间的交互层级，也是整个架构对外暴露的唯一入口。该层不持有任何业务数据，不承担领域计算，其唯一职责是将用户以自然语言表达的意图转化为系统可执行的动作序列，并在指令处理结束后将结果整理反馈给用户。会话层内部由两类Agent构成：会话总控Agent负责接收用户输入、识别操作目标并决定调度哪个下层Agent介入，对需求工程的领域语义保持不透明；计划Agent承接会话总控的委托，根据拓扑模板将用户意图拆解为具有先后依赖关系与显式成功标准的有序步骤序列，并在执行过程中依据中间结果动态调整路径，并时刻指导下层Agent执行命令。当步骤输出未达预期时，由计划Agent判断应触发重试、执行降级还是向上发起用户澄清。

执行层承接所有资源密集型、逻辑确定性的计算任务，将重计算与长耗时执行从核心编排路径中分离，以避免阻塞交互的主干。执行层由多个分层的专项Agent组成。专项Agent负责特定业务领域的语义判断。例如，需求管理Agent是系统唯一具备写入权限的专项Agent，负责将修改意图转化为结构化变更命令并经由领域层落地；质检Agent对单条需求执行结构化质量评判，覆盖完整性、可测试性、明确性与一致性四个维度，输出携带具体问题定位的结论而非简单布尔判定；冲突检测Agent专责跨需求的语义裁决，做出需求条目之间是否冲突的判断。专项Agent之间一般不存在直接横向通信，其协作逻辑在绝大多数情况由会话总控通过统一的编排接口驱动。

领域层是整个系统一致性保障的核心，其职责被严格限定为维护每一条需求条目的状态完整性与变更一致性。领域层以RequirementActor为基本组织单元，系统为每一条需求条目分配唯一一个Actor，以requirement_id为寻址依据，该Actor是这条需求数据的唯一权威持有者。Actor采用以命令驱动的事件追溯机制：Actor在收到Command后首先校验前置条件，校验通过则执行变更并将本次变更以不可变的Event追加至事件流；校验失败则直接返回失败原因，不产生任何事件。对同一requirement_id的Command由Actor串行处理，从根本上消除了并发写入冲突，调用方无需实现任何外部锁机制。在生命周期管理上，Actor采用虚拟Actor模式按需激活与自动休眠，使系统在逻辑上可支持海量需求条目而物理内存中仅维持当前活跃子集。

数据底座是整个系统的持久化记忆层，由三类存储组件构成。事件存储以追加写入的方式持久化Actor产生的全部不可变事件，是系统唯一的真相来源；读模型通过订阅事件流异步构建面向查询场景优化的投影视图，实现读写路径的彻底分离；执行图存储记录每条用户指令从到达系统至最终结束的完整执行轨迹，包含所有容器节点与跨容器边；

# 核心建模

## 图的基本元素

1.  节点

节点是图的内部执行单元，代表一次具体的执行动作。每个节点有明确的输入、执行行为与完成信号，节点之间通过边按某种顺序流转。

系统共定义五种节点类型：

| **类型** | **执行模型** | **完成信号** |
|----|----|----|
| start | 透传，接收上游输入并注入当前节点上下文 | 直接流转，无推理过程 |
| llm | input（增量上下文）→output（结构化结果+tool call列表）→tool call results（若有） | 输出匹配output_schema_json即视为完成 |
| handoff | 将流程控制权交回human，挂起当前执行，等待用户确认或补充输入 | 用户输入到达，结果注入当前节点上下文后继续 |
| invoke | 确定性跨容器调用，目标容器在配置中静态指定，payload经Sidebar路由至目标容器 | return边到达，结果注入当前节点上下文后继续 |
| end | 透传，将执行图最终输出返回给调用方 | 节点完成即执行图完成 |

1.  Start节点

start节点是每个执行图子图的入口，职责是接收调用方传入的任务并将其注入当前执行图子图的执行上下文，供后续节点的input选取。它本身不做任何推理或操作，执行即完成，直接流转到下一个节点。

每个执行图子图有且只有一个start节点。任务载荷（task，即调用方传入的委托指令）始终通过start节点作为第一条消息注入，无需在后续节点中重复声明。

2.  llm节点的结构

从系统设计的角度看，大模型本质上是一个复杂的黑盒函数：给定一段输入文本，它产出一段输出文本，内部推理过程对系统不透明。要让这个黑盒函数真正"操控"系统，比如读取数据、触发操作、影响状态，就必须为它提供明确的接口。

解决思路是：让模型输出结构化文本，由系统解析后代为执行。实践中通过tool
call机制实现：模型在输出中声明它希望调用哪些工具、传入哪些参数，系统解析这份声明并执行对应操作，再将执行结果反馈给模型。这样，模型对系统的"操控意图"就被转化为了可被机器处理的结构化指令序列。

基于这一机制，llm节点的一次完整执行可以形式化描述为三段：input、output、tool
call results。

input：喂给模型的输入上下文。节点不接收全量历史，而是从前序执行结果中增量选取与本节点任务相关的消息片段。这一设计使每个节点的推理焦点保持集中，避免无关上下文干扰模型判断。具体的增量机制见下文。

output：模型基于input产出的结构化结果。输出有两种形态：其一是纯结构化结论，直接作为本节点的推理产物向后传递；其二是结构化结论附带tool
call列表，表达模型希望对系统执行的动作序列。列表中的所有调用一次性并行发起，而非逐条串行等待，这使得多个独立操作（如同时读取多条需求状态）可以在单个节点内高效完成。

tool call results：仅在output含有tool
call时出现。系统并行执行所有调用后，将全部结果追加到本节点的上下文中，供模型完成后续推理或供下一节点的input选取。至此，节点完成。若output不含tool
call，则本段不发生，节点在output产出后直接完成。

3.  handoff节点

handoff节点用于将流程控制权从系统交还给用户。运行时到达此节点时，当前执行图进入Suspended状态，系统将挂起点的上下文整理后呈现给用户，等待其确认或补充输入。

handoff节点解决的核心问题是：系统在某些情况下无法自主推进——信息不足、存在歧义、或业务约束要求人工介入：此时不应静默失败，而应在流程中预留一个显式的"交还控制权"节点，让挂起行为成为有据可查的流程事实，而非异常状态。

用户输入到达后，新输入作为增量消息注入到挂起节点的上下文末尾，执行图从Suspended恢复为Running，从handoff
节点处继续推进。全程在同一张执行图内完成，挂起前后依旧能保持完整的运行轨迹。

4.  end节点

end节点是每个执行图的出口，将执行一次的的最终输出传给调用方。对于被invoke节点调用的subgraph，end节点触发return边，将结果回流至发起调用的容器；对于顶层subgraph，end节点的完成标志整个流程路径的结束。

每个subgraph有且只有一个end节点。它本身不做推理或操作，与start节点对称，共同构成subgraph的边界定义。

2.  Edge边

边（edge）表达执行图中的流转关系，定义了节点之间、subgraph之间、或者是容器之间"谁执行完之后流转到谁"的拓扑结构。边不携带业务数据，业务数据通过上下文注入机制在节点间传递；边只负责表达流转事实与逻辑连接。

1.  容器内部边

seq边连接container内部的执行节点，表达节点间的顺序流转关系。它是最简单的边类型：前驱节点完成后，运行时沿seq边推进到后继节点，将前驱节点的output纳入后继节点的增量上下文候选。seq边不跨越container边界，container内部的执行细节对外不可见，外部只感知container整体的入口与出口。

2.  容器间边

容器间边连接不同的container，表达跨容器的协作关系。共三种类型：

call边表示一个容器向另一个容器发起调用。调用方将payload投递给目标container的入口节点，目标container开始执行。call边发出后，调用方容器进入Waiting状态，等待对应的return到达。

return边表示被调用container将执行结果回流给调用方。目标container的end节点触发return边，结果注入调用方发起调用的节点上下文，调用方从Waiting恢复为Running，继续推进后续节点。call与return成对出现，共同构成一次完整的跨容器调用闭环。

retry边表示调用方在收到返回结论后，决定以新的约束条件重新发起调用。与call边的区别在于语义：call是首次委托，retry是基于上一次返回结论的修正重试，执行图中会记录重试次数与每次的约束变化，使重试过程完整可追溯。典型场景是质检不通过后，会话总控将质检结论作为新约束重新委托需求管理Agent。

3.  容器（container）

容器（container）是执行图中的职责边界单元，对应系统中一个具体的执行角色。每个Agent、用户、以及系统组件（如Requirement
Actor）在执行图中各自对应一个独立的container，container的边界即是该角色职责的边界。

container有三种角色类型（role_type）：

| **类型** | **语义**                           | **典型对应**          |
|----------|------------------------------------|-----------------------|
| human    | 用户侧，流程的发起者与人工介入点   | 用户输入、用户确认    |
| agent    | AI推理侧，承载LLM驱动的决策与执行  | 会话总控、各专项Agent |
| system   | 系统侧，承载确定性的状态管理与校验 | RequirementActor      |

container内部包含若干执行节点，节点之间通过seq边顺序流转，构成该container内部完整的执行序列。container对外只暴露入口（start节点）和出口（end节点），内部节点序列对其他container不可见。

container之间通过call、return、retry边通信，所有跨container的调用都经由Sidebar路由，不存在container之间的直接函数调用。这一约束保证了每个container的执行边界在运行时是可追踪、可审计的。

## 执行拓扑图

执行拓扑图是对某一类任务流程的静态建模，描述该类任务"应当怎么跑"的结构约定。它定义了完成这类任务需要哪些container参与、container之间通过哪些边协作、每个container内部包含哪些节点以及节点的类型与执行约束。

执行拓扑图是可复用的。同一类业务意图（例如"修改需求并自动质检"）对应同一张拓扑图，不同用户指令触发时共享这张图的结构定义，不会各自产生独立的结构副本。这意味着拓扑图的设计质量直接决定了所有基于它运行的指令的执行结构是否合理。

执行拓扑图持久存储于系统中，可被编辑、版本化与预览。在运行时执行图尚未完全打通之前，拓扑图本身已经是Agent协作关系的权威表达。职责边界、调用路径、重试约定、挂起点，都在拓扑图层面显式建模，而不是隐含在代码或自然语言约定中。

从与运行时执行图的关系来看，执行拓扑图可以理解为执行图的浓缩与抽象。真实的执行过程往往很复杂，一个节点可能经历多轮tool
call、一条路径可能触发若干次重试，但这些细节都被执行图承载；拓扑图只保留主干，表达的是流程中心路径的结构骨架。运行时执行图在推进过程中始终以拓扑图为参照，每当一个节点完成，运行时在拓扑图上推进对应位置，标记该步骤已完成并确定下一步的流转方向。同时，拓扑图中对每个节点的约束定义会作为建议注入该节点实际的input上下文，告知模型当前节点应当完成什么、输出什么结构，使节点的推理目标在执行时始终与拓扑设计保持对齐。

## 运行时执行图

运行时执行图是某条具体用户指令真实发生的执行轨迹，记录该指令"实际怎么跑"的完整动态过程。

当一条用户指令到达系统时，运行时以对应的执行拓扑图为蓝本，创建一张属于本次指令的执行图实例。此后，该指令执行过程中发生的每一件事都被持续写入这张执行图：每个节点实际收到的input、产出的output、tool
call的发起与结果、跨容器边的流转时序，以及执行中途发生的重试、挂起与恢复。

每条用户指令对应唯一一张运行时执行图，以graph_id作为全局索引。执行图贯穿指令的完整生命周期，从用户输入到达，到流程正常结束、挂起等待或异常终止。中间无论经历多少轮重试、多少次挂起与恢复，始终在同一张执行图上追加记录，而不是创建新的执行图替代旧的。这保证了一次用户意图的完整可追溯性。

运行时执行图最终会进入三种终态之一：Succeeded（正常结束）、Failed（不可恢复错误）、Suspended（等待用户补充输入）。执行图的状态流转将在下一节详细描述。

## 执行状态机

每张运行时执行图在其生命周期内处于且仅处于一种执行状态。状态由运行时框架维护，随节点推进与外部事件到达而迁移。

系统定义五种执行状态：

| 状态 | 含义 | 进入条件 |
|----|----|----|
| Running | 节点序列正在推进 | 执行图创建后初始状态，或从Waiting/Suspended恢复 |
| Waiting | 等待系统内部的异步结果返回 | invoke节点已发出调用，return尚未到达 |
| Suspended | 等待用户的外部输入 | 重试耗尽、Actor校验失败、或handoff节点触发 |
| Succeeded | 执行图正常结束 | end节点完成 |
| Failed | 发生不可恢复错误 | 执行异常且无降级路径 |

Waiting与Suspended是两种性质不同的等待状态。Waiting等待的是系统内部的异步结果，结果到达后由运行时自动恢复推进，无需用户介入；Suspended等待的是用户的外部输入，系统在此主动将控制权交还给用户，直到用户补充输入后才能继续。

Suspended恢复时，运行时不创建新的执行图，而是在原执行图上追加新的输入节点，将用户输入作为增量消息注入到挂起节点的上下文末尾，执行图从Suspended恢复为Running，从挂起点继续推进。一次用户意图始终对应同一张执行图，挂起前后的完整轨迹保持连续。

## 子图（Subgraph）

subgraph是container的子元素，对应拓扑图中用户可见的**一个节点**。它代表一个有明确语义的执行单元，内部包含若干执行节点（node）和内部流转边，共同完成这一语义单元的所有步骤。

核心映射关系：拓扑图中的一个节点=执行图中的一个subgraph。

层级关系：

session（多张执行图的有序链）

└── graph（一张执行图，对应一轮用户意图）

└── container（agent 的职责边界）

├── subgraph A（拓扑图中的节点 A）

│ ├── node

│ ├── node

│ └── edge（subgraph 内部流转）

├── subgraph B（拓扑图中的节点 B）

└── edge（container 级别，连接 subgraph A → B）

subgraph是graph内部的概念，不跨越graph边界。多轮对话的上下文关联由session链在graph层面解决（后一张图的start节点可增量引用前一张图的输出），不通过引入更高层级的subgraph表达。

为什么需要subgraph

根本动机：确定性拓扑与非确定性执行之间的缓冲层

拓扑图是对某类任务的确定性建模——它规定了这类任务应该经过哪些步骤、步骤之间如何流转。但LLM的输出本质上是非确定的：同一个节点在不同上下文下可能产生不同数量的tool
call、不同的推理路径、甚至需要多轮才能完成预期的语义目标。

如果拓扑图的每个节点与LLM的每次推理动作严格一一对应，任何执行细节的变化都会破坏拓扑结构的稳定性。引入subgraph的根本目的，是在拓扑图节点（确定性）和内部执行步骤（非确定性）之间建立一个缓冲层：拓扑图的一个节点对应一个subgraph，subgraph对外承诺语义完整性，对内允许执行步骤灵活伸缩。这样，即便LLM的执行过程与预期有所偏差，只要subgraph的入口和出口语义不变，拓扑结构就保持稳定，整个流程仍能正常推进。

在纯平铺节点模型中，拓扑图的"节点粒度"与"执行步骤粒度"处于同一层次，这会进一步带来两个具体问题：其一，语义粒度与执行粒度耦合——一个逻辑步骤（如"获取所有需求信息"）被迫等价于一个LLM推理动作，无法表达内部有多步执行；其二，拓扑图难以阅读——执行细节和业务语义混在同一层，高层视图因执行细节过多而失去可读性。

与container的核心区别:

| 维度 | container | subgraph |
|----|----|----|
| 层级 | graph的直接子元素 | container的子元素 |
| 语义 | agent的职责边界 | 一个语义单元，对应拓扑图的一个可见节点 |
| role_type | 有（human/agent/system） | 无 |
| 跨容器边 | 通过call/return边与其他容器通信 | 不参与跨容器通信，仅在所属container内部被引用 |
| 可复用 | 否 | 是（多个container可引用同一subgraph定义） |

## Actor

Actor是系统架构中领域层的核心组件，也是执行图中的一类特殊container。与承载Agent推理逻辑的container不同，Actor
container不进行任何自然语言推理，其唯一职责是作为单条业务对象生命周期与状态变更的绝对权威持有者。在本系统中，每一条需求条目对应唯一一个
RequirementActor，以requirement_id作为全局寻址依据。

Actor采用命令驱动的事件溯源机制处理写入。当外部container通过call边向Actor投递Command时，Actor首先在内存中完成前置业务校验——例如，已基线的需求拒绝一切内容修改命令；校验通过后，Actor构造对应的不可变Event并追加写入事件存储，事件落库确认后才将其应用于内存状态并递增版本号，最终通过return边将执行结论回流给调用方。校验失败时，Actor直接返回拒绝原因，不产生任何事件，状态不发生任何变化。这一流程从根本上保证了每一次状态变更都有迹可查、可回放、可审计。

并发安全是Actor存在的核心动机之一。每个Actor实例持有一个专属的串行信箱（mailbox），所有针对同一requirement_id的命令必须进入这个信箱排队，Actor每次只出队一条消息处理。这意味着对同一条需求的并发写入在物理上被序列化，调用方无需实现任何外部锁机制，写入冲突从架构层面被彻底消除，而非依赖数据库层的悲观锁或乐观版本冲突重试。

Actor的生命周期对外完全透明，采用虚拟Actor（Virtual
Actor）模式管理。Actor
Manager负责按需激活与自动休眠：当某个requirement_id的命令到达时，Manager检查对应Actor是否在内存中，若不在则自动完成实例化、从快照和增量事件中重建状态、启动信箱消费协程，整个激活过程对调用方不可见。当一个Actor超过闲置阈值且信箱排空后，Manager会在落库快照确认成功的前提下将其从内存中卸载。快照写入失败时，Actor不会被回收，避免状态在内存中消失但持久化尚未完成的数据丢失风险。这一机制使系统在逻辑上可支持任意数量的需求条目，物理内存中仅维持当前活跃子集。

在故障语义上，Actor将异常分为两类：DomainException表示业务规则不允许，直接返回失败，不重试；InfrastructureException表示基础设施故障，按指数退避策略重试，超过最大重试次数后Actor进入熔断状态，并主动清空信箱中的积压请求，向每个等待方返回明确错误，避免调用链无期限挂起。

在读写分离上，Actor提供两条查询路径。Actor
Ask允许调用方向信箱发送QueryState命令，Actor处理到该命令时直接返回内存中最新的状态，一致性最强，适用于写后即读的工具链场景。对外部查询则通过读模型和版本围栏（Version
Fencing）机制支持：写操作返回的版本号可作为min_version参数传入查询，若读模型尚未追及该版本则轮询等待，超时后返回503，避免查询端无期限阻塞连接资源。

## 会话链

每轮用户输入对应一张独立的运行时执行图。同一个会话（session）内的多轮交流，通过session链将这些执行图串联，而不是把多轮交流合并进一张大执行图。

这一选择的核心理由是：单张执行图代表一个原子意图，其生命周期、终态、Checkpoint
机制都以这个粒度为基础，粒度上移会让这些机制的边界模糊；而多轮可追溯性的需求，通过图之间的显式链接同样可以满足，不需要在图内部引入新的层级。

1.  Session链的结构

每个 session 维护一条有序的执行图引用链：

session_id

└── graph_id_1（第 1 轮）→ graph_id_2（第 2 轮）→ graph_id_3（第 3
轮）...

每张执行图记录两个关联字段：

session_id：所属会话

prev_graph_id：前一张执行图的ID（第 1 轮为空）

2.  跨轮上下文的引用机制

后一轮执行图的 start 节点在初始化时，可以从 prev_graph_id
对应的执行图中增量选取与当前意图相关的上下文片段注入。具体选取哪些内容由节点配置决定，常见策略包括：

引入前一轮的用户输入与会话总控最终回复（最小上下文）

引入前一轮中某个专项 Agent 返回的结构化结论（如上一轮的质检结论）

不引入任何前置上下文（当前指令完全独立时）

这与llm节点的增量上下文机制一致：后轮start节点不是默认拉取全量历史，而是声明式地选取所需片段，避免随轮次增加上下文无限膨胀。

3.  与Suspended状态的区别

| 场景 | 建模方式 |
|----|----|
| 同一意图中途需要用户补充信息 | 当前执行图进入 Suspended，用户输入后在原图上恢复 |
| 用户完成一轮对话后发起新的意图 | 当前执行图结束（Succeeded），新建执行图，通过 session 链引用前图上下文 |

判断标准是意图的连续性：用户是在推进同一件事，还是发起了一件新的事。前者是Suspended
恢复，后者是新建执行图并链接。在实践中，这个判断由会话总控的intent_parse
节点负责，它在识别意图时同时判断当前轮次是否属于上一张执行图的延续。

# 会话层

## 职责

会话层是用户与系统之间的唯一交互入口，也是整个架构对外暴露的唯一界面。会话层不持有任何业务数据，不承担领域计算，其核心职责是意图理解、流程编排与结果呈现。

会话层主要由会话总控Agent构成。它是系统对外的唯一门面，负责接收用户以自然语言表达的输入，识别操作目标，决策调度哪个下层Agent介入，并在流程结束后将执行结论整理为自然语言回复用户。

会话总控对需求工程的领域语义保持不透明，它只判断"该做什么"，不理解"需求本身的业务含义"。领域语义的判断由执行层各专项Agent负责；会话总控只负责将用户意图转化为可执行的委托指令，并在收到执行结论后将其还原为用户可读的回复。

## 会话总控 Agent的设计

会话总控Agent是系统对外的唯一入口，用户的所有输入均由其接收，所有回复均由其输出。系统内部的执行细节对用户不可见，用户只与会话总控交互。

会话总控的职责严格限定为三项：识别用户意图、编排委托指令、呈现执行结论。它不持有任何需求业务数据，不对需求内容做任何语义判断，对需求工程的领域语义保持不透明。

在编排职责上，会话总控决定将用户意图拆解为哪些委托指令、以何种顺序投递给哪些执行层Agent，并在收到返回结论后决定是否需要进一步委托。但它不介入执行层Agent的内部推理过程，也不对返回结论的业务正确性做判断——结论是否符合预期，由计划Agent或执行层自身保证。

会话总控是系统中唯一感知完整用户意图的角色，也是唯一负责在多个执行结论之间建立关联并统一回复用户的角色。

# 执行层

## 职责

执行层承接所有业务语义判断与资源密集型操作，是会话层委托指令的实际承载者。执行层不感知用户输入，不负责意图理解，也不产出面向用户的自然语言回复；它只处理结构化委托、返回结构化结论，执行边界在接收调用方payload时开始，在向调用方回传结论时结束。

执行层由多个专项Agent构成，按职责性质可分为四类：

| **类型** | **Agent** | **职责简述** |
|----|----|----|
| 写入类 | 需求管理Agent | 需求状态的全部变更操作，系统中唯一持有RequirementActor写入权限的执行单元 |
| 分析类 | 质检Agent、冲突检测Agent、影响分析Agent、基线变更Agent | 对需求内容或变更动作做结构化语义裁决，输出带定位的结论 |
| 生产类 | 需求抽取Agent、需求分类Agent、需求追溯关系Agent、测试映射Agent、评审纪要Agent | 从原始输入或现有需求中派生出新的结构化产物 |
| 支撑类 | 知识检索Agent、执行图观测Agent | 为其他Agent提供证据检索或执行图诊断，不参与业务流程本身的推进 |

各专项Agent职责严格隔离，不横向感知彼此的执行过程，也不在彼此之间建立直接调用关系。Agent之间的协作顺序与结论传递，完全由会话层统一编排。这一设计有两层核心考量：其一，职责单一使每个Agent的推理焦点保持集中，不因承担多类语义判断而导致上下文膨胀与行为漂移；其二，横向通信的缺失将协作逻辑的全部控制权收归会话层，使流程结构在执行拓扑图中保持显式可见，而非隐含在Agent之间的私有调用约定中。

在对领域层的访问权限上，执行层Agent遵循严格的读写分离。需求管理Agent是系统中唯一持有写入权限的专项Agent，通过向RequirementActor投递Command完成状态变更；其余所有Agent若需访问需求数据，仅以强一致直读方式与RequirementActor交互，不产生任何写操作。这一约束从架构层面保证了需求状态变更的入口唯一性，使所有写入均可追溯至同一条路径。

# 领域层

## 职责

领域层是整个系统一致性保障的核心，职责被严格限定为维护每一条需求条目的状态完整性与变更一致性。领域层不参与意图理解，不承担语义判断，不产出面向用户的任何输出；它只响应来自执行层的Command，按照业务规则决定接受或拒绝，并以不可变事件的形式记录每一次被接受的变更。

领域层以RequirementActor为基本组织单元。系统为每一条需求条目分配唯一一个Actor，以requirement_id为全局寻址依据。该Actor是这条需求数据在整个系统中的唯一权威持有者——任何对该需求的写入，必须且只能经过这个Actor的信箱串行处理，不存在绕过Actor直接操作底层数据的合法路径。

领域层对外暴露的接口语义极为简单：接收Command，返回执行结论。调用方无需关心Actor当前是否在内存中、是否刚被激活、并发请求如何排队——这些生命周期细节全部由ActorManager在领域层内部透明处理。执行层与领域层之间的全部交互经由Sidebar路由，通过执行图中的call/return边完成，不存在跨层的直接函数调用。

## RequirementActor的设计

1.  基本模型

RequirementActor是领域层的基本组织单元，粒度为单条需求条目。系统为每一个requirement_id分配唯一一个Actor实例，该实例持有这条需求在内存中的完整状态（RequirementState），包括版本号、内容、流转状态、质检标记与溯源链接等核心字段。需求的状态流转受RequirementStateMachine约束，合法状态包括Draft、PendingReview、UnderReview、Approved、Rejected、Baselined、ChangeRequested，非法流转在校验阶段即被拒绝，不进入事件写入环节。

Actor对外不暴露任何外部接口，调用方与Actor交互的唯一手段是发送Command。Actor的内部状态对外不可见，外部只能通过Actor
Ask或读模型查询获取状态的只读投影。

2.  命令驱动与事件溯源

Actor遵循"Command→Event→State"的严密流转模型。每次收到Command，Actor按以下顺序执行：首先在内存中完成前置业务校验，校验不通过则直接返回DomainException，不产生任何事件，状态不发生任何变化；校验通过后构造对应的不可变Event，将其追加写入事件存储（Append-Only），Event落库确认后才将其应用于内存状态并递增版本号，最终向调用方返回新版本号。

这一设计保证了两件事：其一，事件流是系统唯一的真相来源，内存状态只是事件流在当前时间点的投影，随时可通过重放事件重建；其二，写入顺序严格为"先落库、再改内存"，任何基础设施故障发生在落库之前时，内存状态不会被污染。

当前主链路实现的Command包括CreateRequirement、UpdateRequirementContent、ChangeStatus、AddQualityMarker，事件模型在此基础上还为EvidenceLinkAdded、PriorityChanged、Deleted等后续扩展预留了对应的Event类型与apply逻辑。

3.  并发安全

并发安全是Actor存在的核心动机之一。每个Actor实例持有一个专属的异步信箱（asyncio.Queue），所有针对同一requirement_id的Command必须进入这个信箱排队，Actor每次只出队一条消息处理，处理完毕后结果通过Future回填给对应调用方，再出队下一条。

这一机制将并发请求在物理上序列化为单线程逻辑，从架构层面彻底消除了同一需求的并发写入冲突，调用方无需实现任何外部锁、乐观锁或数据库层的版本冲突重试。在集群场景下，由ActorManager结合Redis分布式锁保证同一requirement_id的Actor实例在整个集群中有且只有一个，单节点的信箱串行语义由此扩展为全局唯一写入点。

在故障处理上，Actor将异常分为两类：DomainException表示业务规则拒绝，直接向调用方返回失败，不重试；InfrastructureException表示基础设施故障，按指数退避策略重试，超过最大重试次数后Actor进入熔断状态（is_faulted=true），并主动清空信箱中全部积压Future、向每个等待方返回明确错误，避免调用链无期限挂起。

4.  读写路径

Actor提供两条性质不同的查询路径，分别适用于不同的需求场景。

ActorAsk是强一致路径。调用方向信箱投递QueryState命令，Actor处理到该命令时直接将内存中最新的RequirementState返回，免除一切入库和拉库的延迟。这条路径适用于写后即读的工具链场景，例如需求管理Agent完成写入后，质检Agent需要立即获取最新状态进行评判。

读模型查询是解耦路径。外部查询通过RequirementProjection读模型访问，读模型异步订阅事件流构建查询视图，与Actor内存态完全解耦，避免所有读压力直接落到Actor本身。为解决写后读模型尚未追及的时序问题，查询接口支持min_version版本围栏：调用方将写操作返回的版本号作为min_version传入，若读模型当前版本尚未追及该值，则轮询等待；超过设定超时时间后返回503，由调用方决定是否重试，绝不允许查询端无期限挂起消耗连接资源。

## Actor Manager的设计

1.  职责

Actor Manager
是RequirementActor的运行时外壳，对调用方屏蔽Actor物理存在的全部细节。它维护requirement_id到Actor实例的索引，负责按需激活、定时回收、分布式协调、统计巡检与进程关闭时的整体shutdown。

有了Manager，执行层的调用方只需做一件事：向Manager发送Command，无需关心对应Actor当前是否在内存中、是否刚被激活、集群中哪个节点持有该实例。Manager将这些复杂性完全收敛在自身内部，对外提供与访问单个内存对象无异的调用体验。

2.  激活流程

当某个requirement_id的Command到达时，Manager首先检查内部实例索引。若Actor已在内存中，直接将Command投入其信箱；若不在，则触发激活流程：先向分布式协调器申请该requirement_id的排他锁，拿到锁后实例化空Actor对象，随即从持久化层恢复状态——优先加载最新快照，再重放快照版本之后的增量事件，完成状态重建后启动信箱消费协程，Actor进入可服务状态，Command随即入队处理。整个激活过程对调用方不可见，调用方感知到的只是Command最终被执行并返回结论。

拿不到分布式锁意味着集群中另一节点已持有该Actor实例，当前节点拒绝本次激活并向调用方返回错误，由上层决定重试或转发策略

3.  休眠与回收

Manager以固定间隔扫描全部活跃Actor，对超过闲置阈值（默认10分钟）且信箱已彻底排空的Actor启动休眠流程。休眠须满足两个绝对前提：信箱必须为空，且当前版本的快照必须成功落库。
