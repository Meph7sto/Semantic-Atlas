## Context

当前系统由本地业务后端（`backend_business`）、本地前端（`frontend`）和可独立部署的推理后端（`backend_inference`）组成，用户日常通过本地 `deploy/start.ps1` 启动服务。新增语音转文字功能时，模型推理实际运行在远端 AutoDL 服务器，且项目已配置 FRP 以实现内外网穿透。

该变更是跨模块能力：涉及媒体文件上传、远端 ASR 调用、异步任务状态跟踪、结果回传持久化、前端会话展示与本地导出。现有系统尚无统一的“媒体转写会话”数据模型与生命周期管理。

约束条件：
- 推理模型固定为 `microsoft/VibeVoice-ASR-HF`，推理耗时可能较长。
- 上传文件体积与网络抖动会影响端到端成功率，需要异步化与重试策略。
- 本地与远端部署分离，接口需兼容 FRP 暴露地址与鉴权策略。

## Goals / Non-Goals

**Goals:**
- 提供端到端的媒体转写闭环：上传 -> 远端推理 -> 回传结果 -> 本地会话保存 -> 可导出本地文件。
- 定义明确的转写任务状态机与错误语义，保证前端可观察任务进度。
- 在不改变用户本地启动方式（`deploy/start.ps1`）前提下接入远端推理。
- 为后续多模型扩展保留接口层抽象（至少服务级可替换）。

**Non-Goals:**
- 不在本次变更中实现实时流式 ASR（WebSocket 实时字幕）。
- 不在本次变更中实现多语言自动翻译或说话人分离高级特性。
- 不重构现有全部任务调度框架，仅新增与 ASR 相关的最小必要编排。

## Decisions

1. 采用“本地业务编排 + 远端推理执行”的异步任务架构。
- Rationale: 本地接口快速返回 `session_id` 与初始状态，避免同步阻塞；远端推理耗时与网络不确定性可通过轮询/回调解耦。
- Alternatives:
  - 同步阻塞请求：实现简单但超时风险高，用户体验差。
  - 前端直连远端推理：绕过业务治理，不利于权限、审计、会话持久化。

2. 统一使用 `transcription_session` 作为持久化核心实体。
- Rationale: 将输入文件、请求参数、状态、结果文本、错误信息收敛到单一主表（可扩展子表存 segments），便于查询与导出。
- Alternatives:
  - 仅写日志不建实体：无法稳定支持列表/详情/重试。
  - 直接复用已有聊天 session：语义不匹配，污染现有会话模型。

3. API 采用“创建任务 + 查询会话 + 导出结果”三类接口。
- Rationale: 明确职责边界，便于前端按状态驱动 UI。
- Alternatives:
  - 单一大接口：耦合高，不利于失败恢复与权限控制。

4. 远端推理服务输出标准化结果结构。
- Rationale: 无论底层模型返回形式如何，业务侧统一消费 `text + segments + metadata`，降低耦合。
- Alternatives:
  - 透传原始模型响应：后续模型替换成本高，前端契约不稳定。

5. 导出能力在业务后端实现服务器端生成并下载。
- Rationale: 保障权限控制与审计，避免前端拼装不一致；支持 TXT/JSON 两种格式。
- Alternatives:
  - 前端本地拼接导出：实现快但无法保证数据完整性与一致性。

## Risks / Trade-offs

- [Risk] 大文件上传与远端转发导致超时或失败 -> Mitigation: 文件大小上限、分段上传预留、后台异步处理、可重试。
- [Risk] FRP 链路不稳定导致任务卡死 -> Mitigation: 任务超时状态（timeout）、幂等重试、失败原因结构化记录。
- [Risk] 远端模型冷启动慢影响首帧延迟 -> Mitigation: 服务预热、健康检查、首次请求提示。
- [Risk] 会话结果含敏感语音内容 -> Mitigation: 增加鉴权校验、最小化日志脱敏、可配置保留周期。
- [Trade-off] 先落地轮询而非回调，开发更快但状态刷新有延迟。

## Migration Plan

1. 在业务后端新增 ASR session 数据结构与 API 路由，不影响现有接口。
2. 在远端推理服务新增 VibeVoice 推理入口，并完成服务健康检查。
3. 配置本地业务后端的远端推理地址、鉴权 token、超时/重试参数（通过 `.env`）。
4. 前端新增“语音转写”入口页（上传、进度、会话列表、详情、导出）。
5. 联调流程验证：上传音频/MP4、状态流转、回传文本、会话查询、导出下载。
6. 灰度发布：默认仅对内部角色可见，稳定后开放全量。
7. 回滚策略：关闭 ASR 功能开关并保留既有会话数据，不影响其他业务模块。

## Open Questions

- 远端推理调用采用业务侧轮询还是推理侧回调为主（建议先轮询，后续补回调）？
- 是否需要对 MP4 自动抽取音轨并保存中间产物，还是只保留最终文本？
- 转写结果是否需要“人工修订版本”与“模型原始版本”双版本存储？
- 默认文件大小上限与会话保留时长应设定为多少（需结合存储成本）？
